# 不依赖宿主的设计实验结果

本轮使用固定 Task Request JSON、真实 Windows WPS、独立文档观察和保存文件检查。它回答“这些机制是否按设计工作、有什么代价”，不回答“WorkBuddy 的用户任务完成率提高了多少”。预先声明的判断标准见 [实验方案](host-independent-experiments.md)，全部早期异常见 [失败台账](design-experiment-failures.md)。

**已有真实 Agent 证据：** 9 月 18 日已完成 Word 四例定向回归、Excel/PPT R01 和 Excel R02。与本轮机制实验的综合结论见 [真实 Agent 与设计证据](agent-and-design-evidence.md)。下文“本轮不能支持”的结论仅限定于固定 JSON 实验，不表示此前没有宿主测试。

**本轮已结束：机制、对照和成本实验已完成并取回核验。通信长测按用户要求提前停止，其他快速实验完成后不再复测。**

## 按最终价值维度看结果

| 最终维度 | 本轮可支持的结论 | 尚不能支持的结论 |
| --- | --- | --- |
| 任务达成 | 固定 JSON 可驱动三应用真实修改/保存；动态引用、已完成结果的查询有执行证据 | Agent 是否选对 Action、填对参数、正确理解用户目标，以及真实端到端完成率 |
| 完成效率 | schema 输出体积、启动层数成本、Task 长度成本、正常回读成本有测量 | Agent 思考时间、真实 token、端到端提速比例、没有等价接口的逐 Action 接续对比 |
| 操作安全与结果可信 | 预检避免部分修改，精确绑定避免误改，回读检出漏写；重复提交、中断、超时和保存边界符合所测断言 | 任意故障零损害、多机通用性，或 WPS 原生服务器真正卡死时其他文档仍能响应 |

这些实验中的“通过”指符合提前声明的断言。预期拒绝/unknown/隔离不能算作用户任务成功。

## 有直接对照的四个保护设计

- **提前校验（T02）**：计划末尾参数错误。正式方案在受理前拒绝，真实文档零修改；仅逐步校验的候选已产生一次标记效果后失败。两组均未保存，也均未假报完成。收益是减少失败造成的部分修改，不是把错误计划变成成功任务。
- **精确绑定（T06）**：绑定 A 后激活 B。三应用正式方案只改 A。Excel 活动工作表候选报告成功，却只改 B；独立 COM 观察确认错误目标。候选只用于因果对照，并非一个已经成熟的替代执行器。
- **原生回读（T11）**：两组均受控跳过真实赋值。正式回读检出不一致并停止保存；乐观生成返回值的候选报告成功，而文件和独立 COM 观察都没有目标效果。这直接证明该场景中回读避免了假成功，不是只测试伪造一份 Task Response。

- **逐步回执（T04）**：两组均实际保存后、PDF 派发前终止 Python。正式方案仍知道 Word 3 个、Excel/PPT 各 6 个步骤成功，包含保存；只保留接纳与最终回执的保守候选只能将全部 4/7/7 个步骤标为 unknown。两组都不重放，也都没有假报整个 Task 完成。收益是保留可查询的已知事实，人的排障时间未测。

末尾错误三次重复的失败返回中位数，正式方案 Word/Excel/PPT 分别约 0.098/0.088/0.090 秒；逐步校验候选约 1.865/1.858/1.435 秒。此处衡量尽早失败的成本，不能写成成功任务的提速。

## 其他机制与保证边界

| 设计 | 本轮观察 | 代价/边界 |
| --- | --- | --- |
| 同一路径不重放（T03） | 丢 CLI 最终输出后可查回原结果；重复已消费路径、恢复相同 JSON、并发重复均没有第二次效果；改有效内容报身份冲突 | 同内容换路径产生新的 Task 和第二次效果，不是全局内容幂等 |
| 动态校验与过期观察（T02/T11） | 错误引用路径、引用解析后的非法参数在消费者派发前停止；三应用旧范围/token 及跨 Task 复用观察均拒绝后续修改 | 前面已成功的修改保留；不会自动回滚 |
| 持久回执与中断（T04/T05） | 效果前、效果后但响应未进入回执、保存成功后三种窗口，共三应用九次强制终止；查询报告 interrupted/unknown，保存已知事实保留，同路径不重放 | “效果前”只指目标标记写入；Excel 插行/PPT 空白页等更早步骤可能已完成 |
| Action 响应丢失（T05） | 真实效果已发生但 bridge 未返回响应：Task 报 unknown/RESPONSE_LOST，后续保存停止，原路径不重放 | 并不保证没有效果；调用方须只读核验 |
| Lease（T07） | 同文档第二个提交报 DOCUMENT_LEASE_CONFLICT；save/saveAs 已返回而 Task 未结束时，新保存目标仍被围栏保护；原 owner 释放测试屏障后仅执行一次 | 自动化排他不阻止用户直接编辑 |
| Quarantine、deadline、进程归属（T07/T08） | 协调窗口内效果完成后挂起 bridge，三应用均 unknown、同文档新提交被隔离，其他测试文档可成功；持有原生进程句柄确认 bridge 已退出 | 人为等待发生在真实 COM 调用返回后，不能冒充 WPS 内部调用卡死；隔离会阻止后续自动化 |
| 显式持久化（T09） | 不保存、仅 PDF 导出时原文件哈希不变；已有脏改且未获授权时拒绝；保存冲突不继续 PDF；PDF 冲突仍保留已成功保存的事实 | 失败与无保存的现场保持打开，不进行清理式保存 |
| Task Outcome 与清理分离（T10） | 实际清理完成后注入清理报告失败：文档已保存、Task outcome 仍成功，cleanup 失败、退出码非零；重复不重放 | 这是报告聚合对照；不称原生清理故障覆盖。实际异常桥接退出的清理不确定另有故障证据 |

超时实验设置 Action deadline 为 5 秒；从 CLI 子进程启动到返回分别约 Word **15.29 秒**、Excel **15.47 秒**、PPT **15.15 秒**，均低于预先声明的 25 秒测试上界。包含获取文档、失败确认和清理等待，不能写成“整个 Task 五秒内返回”。

## 效率测量

同一 Windows 11 26200、WPS 12.1.0.28505、Python 3.13.14、桌面 Session 3。包来自当前未提交工作区，基准 commit 不能单独还原；应使用包哈希与逐文件清单。机器已有 WPS 与保留的故障文档，部分测量并行于纯通信检查。不是空闲机器/冷启动实验。正式 bridge 中增加测试日志，因此以下是同等观测条件下的成本。

### 按需 schema

每应用固定选取四个 Action，选定契约及其引用定义与全量输出一致；10 对交替顺序查询。没有先调用 Action Index。

| 应用 | 选定 / 全量 Action 数 | 按需字节 | 全量字节 | 字节减少 | 查询耗时中位数，按需 / 全量 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Word | 4 / 14 | 9,309 | 36,796 | 74.7% | 36.63 / 39.98 ms |
| Excel | 4 / 34 | 4,349 | 26,197 | 83.4% | 33.93 / 37.94 ms |
| PPT | 4 / 37 | 4,268 | 32,330 | 86.8% | 34.86 / 38.56 ms |

这是 `schema.py` 实际 stdout 的 UTF-8 字节数，不是模型 token。选定集合影响减少比例；此处不能推导 WorkBuddy 的实际上下文使用或任务耗时。

2026-09-19 补充离线分词复算：直接读取上述归档 stdout（保留 CRLF），使用 tiktoken 0.14.0 的两套参考编码；没有重新执行 schema 查询或 WPS 测试。按 `o200k_base`，Word 全量/按需为 **9327/2394 tokens（减少 74.33%）**，Excel 为 **6563/1139（82.65%）**，PPT 为 **8344/1144（86.29%）**。`cl100k_base` 对应减少 74.39%/82.85%/86.38%。因此可表述为“固定四 Action 集合的 schema token 占用按参考分词器减少约 74%–86%”；它不是宿主实际模型计费 token、整个会话的 token 减少比例或端到端提速。逐文件哈希与分词结果见 [token 复算](../../build/evidence/design-value/schema-token-counts.json)。

### 外层启动与传输候选

同一 Python 夹具、同一 UTF-8 JSON 文件，输入路径含中文与空格；20 对交替顺序启动。直接 Python 中位数 **37.31 ms**，外套 PowerShell **132.39 ms**。两组内容完全一致。只能归因于该夹具的外层启动差异，不能据此去掉当前负责 WPS COM 的 PowerShell bridge。

三个传输候选均使用同一 Python echo 服务，复用正式严格 JSON transport 和 bridge 响应校验；本机 TCP、命名管道只是可运行的协议夹具。每种 11 种协议异常，**33/33 均映射为 unknown/RESPONSE_LOST**，所有所属进程被回收。异常包括非法 JSON、重复字段、非有限数、错请求 ID、错 outcome、缺/多字段、坏编码、退出、延迟、截断。

每个通道/载荷 10 个独立进程，每进程 20 次请求。以下取各进程后 19 次往返中位数，再取进程间中位数；首响应和启动时间保留在原始数据中。

| 候选 | 32 字符往返 | 4096 字符往返 |
| --- | ---: | ---: |
| 匿名管道 | 0.113 ms | 0.271 ms |
| 本机 TCP，缓冲读写 | 0.143 ms | 0.332 ms |
| 命名管道 | 0.130 ms | 0.276 ms |

本轮没有观察到改换通道明显更快的依据，也不证明匿名管道在所有环境最好。这些候选没有接 WPS COM，未评估完整部署、访问控制、重连和原生绑定语义。

### Task 长度与回读成本

固定已保存小文档，分别进行 1/8/32 次只读 Action，每种三次，轮换长度顺序。下表为含 CLI、文档获取、执行、回执与清理的总时间中位数；不含创建 fixture 与独立观察。

| 应用 | 1 个内容 Action | 8 个 | 32 个 | 32 个时回执发布累计 |
| --- | ---: | ---: | ---: | ---: |
| Word | 1.79 s | 2.47 s | 4.88 s | 105 ms |
| Excel | 1.39 s | 1.71 s | 3.01 s | 110 ms |
| PPT | 1.06 s | 1.34 s | 2.18 s | 85 ms |

27 个长度样本（三应用 × 三种长度 × 三次重复）均核对过：**每个 Task 各自只使用一个 bridge PID，并在该 Task 收尾时确认释放**；没有跨 Task 常驻复用。归档回执中的 27 份进程清理结果与各 Task 的原生 PID 一一对应，见 [生命周期核对](../../build/evidence/design-value/bridge-lifecycle-audit.json)。计时 span 有嵌套，不能全部相加；`task.resources_startup` 只含执行器构造，原生初始化与文档获取在 document Action 内。这里是成本曲线，不是 Task 相对于不存在的逐 Action 接续接口的收益对照。

Excel 正常赋值并保存的真实回读/乐观结果候选，共 **24 对**；每次均独立确认实际文件和 WPS 内容正确。总时间中位数分别 **1649.36 / 1646.64 ms**。配对差“真实回读减乐观结果”的中位数 **6.52 ms**，范围 **−98.25 至 147.85 ms**。小样本波动明显，不能声称省略回读有稳定净提速，更不能将这个夹具结果推广到全部 Action 或大文档。受控漏写时避免假成功的收益则有直接证据。

## 持续通信

最初两小时长测在 1773 个成功短轮次后因诊断状态发布失败停止；不是通信两小时通过。修复后的 10 轮快速检查通过。随后运行 `startup-20260919T125109-a3b38145` 于 12:51:39.877–13:20:32.776 UTC（北京时间 20:51:39.877–21:20:32.776）执行约 **28 分 53 秒**，记录 **6118 轮通过、0 轮失败**，按用户要求停止：`state=stopped`、`stopReason=operator_requested`、剩余预算未执行。归档完成后外层启动器退出码为 0，计划任务为 Ready、LastTaskResult 为 0。**没有完成两小时预算，不作两小时稳定性结论，也不再复测。**

此检查只调用生产 JsonLineBridgeTransport 与所属 PowerShell echo 进程，两个载荷为 32/4096 字符；不调用 COM，不能证明 WPS 持续运行的稳定性。

## 样本与覆盖范围

- `native-repeat-v6`：三应用各三次的常规机制，共 75 组适用场景通过，6 组不适用；不适用项不计通过。
- `native-assertions-v10`：引用链、跨 Task 观察、补强精确绑定/回读断言，共 30 组适用场景通过，6 组不适用。
- `native-fault-v4`：15 组故障场景通过；中断细分为九个实际终止窗口，隔离三例，持久化六种模式 × 三应用。
- `receipt-lease-v13`：9 组通过，包含三对中断回执对照、三应用两种保存后的 Lease 检查和额外预检核验。
- schema 每应用 10 对；启动 20 对；Task 长度每应用/长度三例；回读成本 24 对；最终严格协议矩阵 33 个异常及 1,203 次成功载荷应答。
- 本地测试共运行 238 项，其中 3 项平台条件跳过；其余通过，见 `build/evidence/design-value/local-tests.log`。

这些“组”有的含多个输入或模式，不能当作同一个分母来计算用户任务完成率。早期失败批次仍在汇总中单列，不与最终重复集混合。仍未覆盖真实 WPS 内部阻塞、所有磁盘/断电故障、全部大文档/格式组合、所有 IPC 背压情况和多机器版本；没有测人的诊断时间或共享代码的维护收益。真实 WorkBuddy 的发现、编排、参数生成及若干跨 Task 行为已有昨日证据；本轮没有重新测量最终版本的宿主完成率，也没有对设计的端到端收益作受控对照，详见综合报告。
