# 设计选择与价值验证计划

执行进展：[不依赖宿主的实验方案](host-independent-experiments.md)、[运行结果](host-independent-results.md)。本文件保留原始收益假设与后续宿主实验边界，实际完成范围以结果报告为准。

既有宿主结果：9 月 18 日的真实 WorkBuddy 测试已完成，见 [Agent 与设计实验综合证据](agent-and-design-evidence.md)。下文的新基线/对照是原计划中的补充方向，不表示宿主从未测试，也不授权本轮继续复测。

前置：Action 执行端在已声明范围内通过固定请求验收，已知问题和未覆盖分支单列。这个计划不与 Action 正确性验收混用成功率，不以尚未实现的候选作为现成对照。

## 最终目标与评价维度

让 Agent 借助 Application Skill，在真实、离线的 WPS 中完成用户要求的文档任务。目标包含正确的目标文档、内容和保存/导出结果，并让用户知道实际完成了什么。

评价从用户结果出发：**用户目标 → 评价维度 → 设计的作用与代价 → 对照实验 → 证据**。原来的五类划分保留为实验按实现位置的归档方式，不再作为最终价值维度。下面记录实验前约定的评价方案，实际完成范围及结论见运行结果。

| 最终维度 | 用户关心的问题 | 主要指标 | 补充观察 |
| --- | --- | --- | --- |
| 任务达成 | 在给定条件和预算内，能否把要求的事情做对？ | 独立验收通过的任务数 / 预先选定的任务尝试数 | 各验收项通过情况、失败原因、人工介入；若另做纠错实验，首轮与修正后完成率分开 |
| 完成效率 | 得到合格结果要等多久、付出多少操作和资源？ | 用户请求提交到合格结果交付的端到端耗时，与任务达成率一起报告 | 失败/超时耗时、人工介入次数与时间、真实模型 token（若可得）、工具调用数、执行阶段耗时和峰值内存 |
| 操作安全与结果可信 | 是否误改、重复写入、非预期保存，是否把未完成说成完成？ | 误改/重复效果/非预期持久化事件，假成功和错误状态报告，及其次数、频率和影响 | 故障后新增的文档损害、保留的已知结果、误拒绝与隔离造成的可用性代价 |

任务达成和完成效率是两个主结果；操作安全与结果可信是必须单独报告的约束。三者不强行加权成一个总分。一次无副作用的提前拒绝和一次破坏文档的失败，完成率上都可能是失败，但对用户的损失不同，需要第三个维度区分。

### 指标口径

1. **按用户任务计完成率。** 不是按 Action 数或返回 success 的 Task 数。每个样本先写明内容、计算、结构、格式、目标文档、保存/导出和交付要求，再用独立产物检查或明确的人工标准验收。重要的错误最终报告会使整体交付不合格，同时在“结果可信”中记录误报事件。清理失败单独记录，不自动推翻已核实的文档效果。
2. **质量属于完成标准。** 开放式任务可以预先约定分项评分，但“做了一部分”不能计为完整完成。执行器自己的响应不能作为唯一效果证据。
3. **固定时间预算与介入规则。** 一次用户请求内允许多次正常工具调用。当前基线遵循失败即停，不因能修正就自动重试。人工修改 JSON、产物或补提示的尝试单列，不能算原轮自主成功。后续若研究 Agent 纠错，另设规则和实验，不改变原 Task 不重放、不恢复执行的约束。
4. **完成率与时间一起看。** 只统计成功样本的平均耗时会遗漏失败和超时。同时报告成功耗时分布、失败/超时数量和耗时、固定时间预算内的完成率。对照使用同一批任务，另说明共同成功样本上的速度差异，避免两组只完成了不同难度任务。尽快失败不能等同于更快完成。
5. **成本有明确边界。** Agent 思考、schema 查询、执行、验证和报告共同组成端到端时间；bridge 等待不能全记为通信耗时。安装/首次配置单列。文件字节、工具调用数是机制指标，不能冒充真实 token 或用户总耗时。
6. **正常任务与故障注入分开统计。** 预期拒绝或隔离成功说明保护有效，不计作用户任务完成。安全指标记录事件数、机会数和影响；小样本未观察到误操作只能报告该样本的 0/N，不推导真实风险为零。

### 适用范围与稳定性

所有结果都要说明“对哪些任务、在哪些环境下成立”。任务类型、复杂度、Word/Excel/PPT、文档规模、Windows/WPS/宿主/模型版本、冷/热启动和运行时长是结果的分组条件。不能通过只选容易任务得到高完成率后，宣称支持任意任务。

能力范围回答“能做哪些事”；上述三项指标回答“在这个范围内做得怎样”。稳定性通过同条件重复和长时间运行中的完成率、耗时、错误及资源趋势来观察；跨机器能力需要多机器证据。这些不再另起一套与完成率重叠的最终分数。

## 每个设计为什么有助于目标

以下是待验证的收益假设，不是已经证明的提升。一个设计可以改善一个维度，同时让另一个维度付出代价。

| 设计 | 主要服务的最终维度 | 作用路径与可测证据 | 代价或不能直接推出的结论 |
| --- | --- | --- | --- |
| Application Skill 与真实 WPS 执行链 | 任务达成 | Agent 能发现能力、形成有效请求，让真实文档达到要求；用真实宿主端到端验收 | 85 个 Action 基线不证明 Agent 会正确使用；没有公平替代方案时只证明当前组合能做到 |
| 用途表、明确 schema、按需加载 | 任务达成、完成效率 | 选对能力、填对参数；比较填写错误、端到端完成率和耗时；无宿主时先量化加载数据量 | 按需查询有调用开销；字节减少不自动带来更高完成率或更低模型耗时 |
| Task 预编排与结果引用（T01） | 任务达成、完成效率 | 动态 ID/范围/token 能贯通，减少调用方中间传参的需求；测引用链、实际启动数和总耗时 | 当前无等价逐 Action 接续接口，不能宣称节省了特定轮次；预编排限制中途重新决策 |
| 静态和动态校验（T02） | 操作安全与结果可信；可能减少失败处理成本 | 阻止无效步骤进入原生调用，减少部分修改；比较错误触发前后的文档效果和耗时 | 校验不会自己修正 Agent 的计划；拒绝不等于完成，不保证增加完成率 |
| 提交身份与不重放（T03） | 操作安全与结果可信；保留已完成结果有助于任务交付 | 丢失最终输出后查询或同路径提交仍只有一次效果，能取得原结果 | 回执查询和存储有成本；同内容换路径是新提交；Agent 是否正确使用还需宿主实验 |
| 持久回执、失败/不确定时停止、清理分开报告（T04/T05/T10） | 操作安全与结果可信；可能减少排查与人工处理成本 | 不丢已知完成事实、不把不确定说成成功、不扩大故障；比较误报、后续派发和故障损失 | 有磁盘 I/O；停止可能降低当次完成率；诊断资料完整不等于人工处理已被证明更快 |
| 精确文档绑定、显式持久化（T06/T09） | 操作安全与结果可信；保护任务要求中的目标和保存边界 | 切换窗口不误改；只按明确意图保存/导出；独立检查目标和非目标文档 | 约束可操作方式；安全检查通过不意味着内容目标完成 |
| Lease、Quarantine、deadline 与进程归属（T07/T08） | 操作安全与结果可信；限制失败占用的时间和资源 | 阻止并发冲突与在途调用重入；测文档损害、返回上界、进程遗留和隔离阻塞 | 可能拒绝本来能继续的任务、增加等待或人工处理；有界失败不等于成功更快 |
| 原生回读、结果契约、观察有效性（T11） | 操作安全与结果可信；提供任务验收所需的执行事实 | 检出效果不符和失效观察，减少假成功；比较漏检、误拒绝和回读成本 | 检出错误不会自动修复效果；增加原生往返，观测到的成功率可能下降但更真实 |
| 三应用共享机制与 trace（T12） | 间接支持任务达成、完成效率和可信度 | 当前能测公共故障分类一致性、诊断完整性；研究维护收益则另测修复/定位工作 | 维护方便主要是工程收益，不能直接宣称用户任务更快；共享缺陷可能影响三端 |
| 启动链、通信策略和环境检查 | 任务达成、完成效率；失败说明支持结果可信 | 减少环境失败、启动等待和长期泄漏；测不同环境的成功率、时间与资源趋势 | doctor 发现问题不等于解决问题；减少启动层数或更换传输方式不预设有收益 |

例如，对原生回读应提出“是否减少假成功，代价是多少时间”，而不能预设它同时提高完成率和速度。对 Task 预编排应分别提出“能否完成动态依赖”和“在公平条件下能否降低完成成本”。实验允许得到没有明显收益，或收益不足以抵偿代价的结果。

## 怎样把局部证据接回最终目标

**完整链路基线**回答“用了当前 Skill，Agent 能否达成用户任务”。它能测实际完成率、时间和误操作，但单独一次基线不能将结果归因于某个设计，也不能宣称优于未测试的方案。

**单项对照实验**回答“某个设计通过什么机制带来收益、代价是多少”。没有宿主也能直接测误改、重复效果、假成功、隔离和执行成本；对 Agent 填参、思考时间、最终任务达成率的影响仍需模型或宿主验证。不能把“少返回一半 schema 字节”直接写成“任务快了一半”，也不能把“拦住错误”写成“完成了任务”。

每个实验用同一条说明串起来：**针对什么失败或浪费 → 哪个设计 → 改善哪个最终维度 → 用什么对照和指标检验 → 付出什么代价 → 目前证据支持到哪里**。下面的执行清单服务于这条关系。

| ⑤ Task 故障保障 | 中断事实保留与失败停止（T04/T05/T10） | 在派发前后、效果产生后、保存后受控中断；单独丢 bridge 的 Action 响应或让 cleanup 失败 | 回执已知部分准确；无法确认效果时报告 unknown；不继续派发或重试；保存结果与 cleanup 分开 | 仅最终回执、受控重试候选分别比较，不同时改多个因素 |
| ⑤ Task 故障保障 | 精确文档绑定（T06） | 绑定测试 A 后主动激活测试 B，再执行修改 | A 达到预期；B 内容和磁盘均不变；误改次数 | 活动文档路由候选，仅对测试 A/B 使用 |
| ⑤ Task 故障保障 | 并发互斥与异常隔离（T07） | 两进程争用一文档；保存/另存前后竞争；超时或 owner 丢失但原生调用可能仍在执行 | 未隔离重入为零；不误挡无关文档；记录拒绝数和隔离代价 | 确认静止才允许后续进入；普通 Python sleep 不能冒充在途 WPS 调用 |
| ⑤ Task 故障保障 | 有界返回与进程归属（T08） | 原生调用、管道或 cleanup 阻塞，终止所属调用方 | 返回和清理时间上界、遗留 bridge 数、围栏终态、其他文档不受影响 | 先做受控进程夹具，再做真实文档；不能把杀掉 bridge 当作 WPS 内部动作已停止；正常运行成本关联④ |
| ⑤ Task 故障保障 | 显式持久化与部分完成（T09/T10） | 无 completion、仅导出、已有脏修改、save/PDF/cleanup 分别失败 | 磁盘是否只按意图改变、保存与导出先后、部分完成是否如实报告 | 专用测试文档；对隐式保存/单一总状态候选分别比较 |
| ⑤ Task 故障保障 | 三应用一致性与诊断证据（T12） | 将同一公共故障矩阵参数化到三应用 | 错误分类、停止、清理一致性，阶段/Task/Action 证据缺失率 | 是⑤的横向复测，不另算第六类；不用这些指标直接宣称维护成本下降或人工定位更快；定位时间需另设人工实验 |

必须区分两处“丢响应”：**调用方没拿到最终 CLI 输出**时，Task 可能已完整成功，应该查询持久回执；**bridge 没返回某个已派发 Action 的响应**时，执行器可能无法确定文档效果，需要停止并按实际情况隔离。前者不要求一个仍在正常执行的 Task 因 stdout 丢失而停止。

| 端到端整体验收 | 自然语言端到端基线 | 必须观察选 Action、查 schema、填参、编排、读回执、最终报告及用户目标达成 | 若结论是当前 WorkBuddy 组合可用，就必须；这是最重要的整体验收 |

## 更新后的执行顺序

1. 先做直观且判定明确的一组：尾部静态错误、同路径重复提交、切换活动文档、回读检错及过期观察。复用已有 v6 正常夹具，增加独立效果判定和单因素对照。
2. 再做中断与隔离：持久回执窗口、bridge 丢响应、并发 Lease、超时 Quarantine、Job Object、持久化与 cleanup 部分失败。同步跨三应用核对公共机制和诊断证据。
3. 再做成本和稳定性：计划长度、回读/回执成本、schema 数据量、启动分轴对照、快速与长时运行。数据也允许得出没有收益或收益不足的结论。
4. 最后固定三应用安装包、WorkBuddy/模型和提示词，执行新会话一次完整需求的端到端基线，然后才比较 schema 提供策略。宿主中断等场景单列归因。

每个实验先写明最终评价维度、设计收益假设、可能代价、测试位置、关联设计点、判断标准、重复次数、测试版本、注入位置、独立效果依据与公平候选。先保留固定版本基线，再做候选；成功和失败都记录，意外失败停下定位，不重放原 Task。新提交使用新路径，仅“不重放”实验明确要求的重复路径例外。

故障候选仅在测试副本和专用文档中运行，不改变正式默认保护。没有公平候选时报告机制正确性和成本；不把故意移除保护的实验候选描述成成熟替代产品，也不把此类对照当作总体性能优越的证明。

## 明确排除的误解

- 当前流程是 SKILL.md 用途表 → schema.py 批量查询 → Task JSON，不要求先执行 --index。
- 目前没有公平的“Agent 逐 Action 继续同一个 Task”接口。拆成多个 Task 会改变绑定、token、重新打开和保存条件，暂缓该对照。
- WorkBuddy 对话上下文、Bash/沙箱环境、Python/bridge 进程和旧 Session 不是同一个生命周期。历史 Q4 证明过特定样本可先读再改，但此前 Session 丢失根因未确认，不把它当作已证明的设计收益。
- 一个用户需求内多次工具调用不等于要求用户持续多轮追问；首轮样本不依赖跨命令保活或用户隔很久再接续。
- 文件字节数不等于模型 token；执行器成功不等于用户目标达成；自动响应断言不等于人工视觉验收。
