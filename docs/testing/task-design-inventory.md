# Task 设计点与可验证收益盘点

2026-09-19。最初基于当前工作区实现、测试代码与有效 ADR 0031 作静态盘点；后续新增的实机执行证据见 [不依赖宿主的实验结果](host-independent-results.md)。历史 ADR 0028/0029 已被后续决策替代，仅作动机背景，不作为当前接口契约。

9 月 18 日真实 WorkBuddy 已有端到端样本，其与机制实验的对应关系见 [综合证据](agent-and-design-evidence.md)。

“有实现”“已有测试”“已用 Windows 故障实验证明”“相对另一方案更好”是四种不同结论。已有测试指下面能找到对应测试代码，不表示已经覆盖所有崩溃窗口、三应用和真实 Windows 情况。

## 设计点

T01–T12 是本盘点的设计点编号，用于追溯实现与测试，不代表验证层次、测试轮次或优先级。例如 T02 是静态和动态校验，T06 是精确文档绑定。设计价值按“任务达成、完成效率、操作安全与结果可信”评价；五类实验仅按实现位置归档。最终维度、收益假设、代价和宿主依赖见 [设计价值验证计划](design-value-plan.md)。

| ID | 当前设计 | 预期收益 | 代价或边界 | 最有辨识度的验证 |
| --- | --- | --- | --- | --- |
| T01 | 一份预编排 Task，文档获取一次，同一 Task 内复用 bridge 和绑定 | 减少反复启动及调用方生命周期管理 | 步骤间不等待 Agent 重新思考；计划有误需要新的 Task；不等于事务 | 随步骤数增长测 bridge 启动数、总时间、内存；当前无等价的逐 Action 宿主提交接口，比较候选需另行实现和验证，暂不列为可直接执行的对照 |
| T02 | 执行前静态校验，结果引用解析后再次校验 | 早拒绝已知错误，阻止动态错误参数进入原生调用 | 增加校验成本；未知结果无法全部提前校验 | 第 N 步静态错误时原生调用数为 0；动态错误时消费者及后续调用数为 0；对照仅运行时校验 |
| T03 | 规范化输入路径作为提交身份，原请求不可变，进程锁独占接纳 | 重复提交、并发提交和 stdout 丢失后不重复产生效果 | 同内容换路径是新 Task；不是全局幂等或 exactly-once；需要保留历史请求 | 同路径重复/并发提交；改内容冲突；丢 stdout 后查询；统计实际效果次数与执行 owner 数 |
| T04 | 请求、初始回执先持久化，派发前记录 running，返回后记录响应 | 进程丢失后保留已知事实，不将可能发生的效果误报为未执行 | 多次磁盘写入；派发前记录与原生调用之间崩溃可能保守标为 unknown；不宣称抗所有断电故障 | 在每个持久化/派发窗口终止进程；比较逐步回执与仅最终回执的误报数、未知步骤数及写入成本 |
| T05 | failed / unknown 区分，均停止后续步骤，无自动重试、回滚或恢复执行 | 避免扩大部分失败、重复写入和不确定保存 | 已有修改保留；需要人工或新请求处理，自动完成率可能降低 | 写入成功后丢响应；断言仅一次效果、后续未执行；用受控候选模拟自动重试并统计重复效果 |
| T06 | 一个 Task 固定一个精确 Document Binding，不随活动窗口变化 | 防止编辑错误文档或中途换目标 | 不可在 Task 内切换文档；不能按活动窗口接管其他 Task 未保存文档 | 同时开 A/B；绑定 A 后切焦点到 B，断言仅 A 改变；对照活动文档路由 |
| T07 | acquisition guard → Document Lease；文件身份及路径围栏跨保存保持；未确认静止时保留 Quarantine | 阻止同一文档并发冲突及超时后重入 | 串行化、拒绝冲突；隔离会降低可用性，需要明确解除条件 | 双进程竞争同一文件，保存替换/另存后竞争；超时但原生仍在执行时新 Task 不得进入 |
| T08 | Action deadline、限时清理、Task 拥有 bridge，使用 Windows Job Object | 有界返回、控制桥接遗留和进程归属竞态 | 超时不能证明 WPS 内部动作停止；不拥有 WPS 应用进程；需保留隔离 | 卡住原生调用、清理或管道关闭；测响应/清理上界、bridge 遗留数量、WPS 状态和围栏状态 |
| T09 | Persistence Intent 显式；默认不保存，未授权已有脏修改时拦截保存型 Task；save 在 PDF 前 | 不擅自持久化用户修改，完成顺序可预测 | 编辑成功可以仍未保存；部分完成不能视作全部成功 | completion 为空、只导出、已有未保存内容、保存失败、PDF 失败；检查磁盘与回执的分别结果 |
| T10 | Task Outcome 与 cleanup 分开报告 | 清理失败不抹掉成功保存，也不成为重新执行理由 | 调用者不能只用退出码推断文档是否成功 | 保存成功后注入清理失败；回执保留保存成功、清理失败；重复提交不增加效果 |
| T11 | Action 内置原生回读、结果契约和语义检查，Task 按验证结果推进；观察令牌/Revision 属于 Task | 减少假成功、失效观察驱动的写入，不依赖 Agent 自编 checks | 增加原生往返；只验证受支持效果，不证明文案正确或用户意图满足；Action 覆盖有差异 | 伪造成功但不改文档、返回非法结构、读取后外部改动、跨 Task 使用令牌；比较漏检率及回读成本 |
| T12 | 三应用共享 Task 机制，应用契约和 Adapter 独立；统一 Task/Action trace | 共用修复，便于横向定位同类故障 | 共享缺陷可能影响三端；日志和维护有成本 | 同一故障矩阵参数化跑三应用，比较分类/停止/清理一致性；定位收益需测定位时间或缺失诊断率 |

## 优先做的设计实验

1. **不重放（T03/T04/T05）**：先写入再丢回执，再提交同一路径。效果次数必须为 1，后续步骤不能越过不确定状态。这最容易展示为什么查询回执优于重新执行。加测换路径会被视为新提交，明确保证范围。
2. **超时后的故障隔离（T07/T08）**：让调用超过 deadline 后仍可能执行；旧 Task 有界返回，新 Task 不得抢占该文档。测隔离正确性，也记录被阻塞的可用性代价。
3. **精确文档绑定（T06）**：A/B 两份文档切焦点，检查写入对象。直观证明绑定的作用，不需要复杂性能统计。
4. **早校验（T02）**：长计划尾部放已知非法参数。断言零文档效果；与延迟校验比较此前已产生的修改数。
5. **一次 Task 的成本（T01/T04/T11）**：分别测启动次数、校验、回读、回执 I/O 和总耗时。对照必须执行语义相同的工作，包含同等验证与持久化要求；不能用删掉校验后的速度直接证明新方案更好。

先复用已有测试中的受控 Adapter 和进程夹具；危险候选只在测试副本/专用文档中运行，不能修改正式默认行为。每个对照只改一个因素，保存成功和失败证据。若没有公平可执行的对照，只报告机制正确性，不给相对收益结论。

## 实验判定模板

记录设计 ID、前置条件、故障注入阶段、当前方案与候选差异、预计文档效果、预期回执与停止点、资源终态、硬性断言、性能指标、重复次数及证据位置。预期故障并不等于实验失败；是否通过按事先声明的断言判断。

正确性指标优先：重复效果数、误改文档数、失败后派发数、假成功数、未隔离重入数应为 0。其次测耗时/内存/启动次数、隔离造成的拒绝与人工处理成本。设计可以正确但没有速度收益，也可以在速度更快时付出不可接受的错误代价。


## 对照可行性修正（按用户补充与当前接口核对）

- 当前正式发现流程为 **SKILL.md 内的 Action 用途表 → schema.py 批量查询所选定义 → 编排 Task**。不要求宿主先调用 `--index`。若比较 schema 加载策略，两组都保留同一份用途表与 Task 流程，只比较按需定义与全量定义；不能把收益归为一个未实际调用的 Action Index 命令。离线输出字节数仅证明载荷差异，不等于 WorkBuddy 实际输入 token 或成功率收益。
- 当前仅暴露完整 Task 提交，不支持把旧 Task 暂停后逐 Action 继续。range/revision/token 属于 Task，未保存文档也没有跨 Task 接续入口。拆成若干 Task 会引入重新打开、重新读取和保存等语义差异，不能直接当作“一次 Task vs 逐步 Action”的公平对照。暂缓该对照，不为了证明收益先复活 Session。
- 结果引用先验证能力：用实际运行才产生的范围、token、slide/shape ID 串联后续步骤，检查是否无 Agent 中间补参完成、引用解析是否正确、无效引用是否及时停止。可以报告编排能力与完成率，但没有等价对照时不报告节省了多少轮或提高了多少成功率。
- WorkBuddy 的“多轮”需区分用户追加消息、一个用户请求内的多次工具调用、多个 Task、跨命令存活进程。既有 Q4 报告包含只读 Task 成功后新的修改 Task 成功，证明该特定旧样本可跨 Task 使用返回正文；不能据此证明长期会话或沙箱生命周期稳定，也不能认定用户此前的 Session 丢失由 WorkBuddy 主动清理造成。
- 新端到端基线优先使用新会话中的一次完整用户需求；Agent 可以在其中多次查询工具，但不依赖交互等待时保活 Python/bridge。记录宿主中断单列归因，不从端到端失败数里悄悄排除。
- 目前可先做：真实用户任务完成与正确报告、动态结果引用贯通、静态 schema 输出量对比、原生回读错误检出及成本、固定输入下的 Task 阶段成本、既定故障保护实验。启动策略候选需保持绑定/验证语义后另行评估。
