# 真实 Agent 与执行机制的综合证据

整理日期：2026-09-19。依据 9 月 18 日已归档的 WorkBuddy 会话、请求、回执和计时汇总，以及 9 月 19 日执行端和设计实验。不启动新测试、不覆盖历史失败。

**真实 Agent 已有端到端执行证据：它能够从自然语言需求出发，自行读取 Skill、查询定义、生成请求，并操作真实 WPS、保存和报告。今天补充的是执行机制的保护价值和成本证据。** 尚未得到的是当前最终版本在统一条件下的全面验收，以及各项设计对 Agent 完成率、总耗时的因果提升比例；不能表述成“真实 Agent 尚未测试”。

## 1. 昨天究竟完成了什么

以下“最终交付”按历史报告中的成功保存/导出回执及交付记录计，不等于人工内容、版式验收，也不自动排除过程违规。

| 批次 | 最终交付回执 | 全程无非成功提交的用例 | 提交成功，含入口拒绝 | 已执行 Action 成功 | 证据性质 |
| --- | ---: | ---: | ---: | ---: | --- |
| Word 四例重测 | 4/4 | 4/4，均只提交一次 | 4/4 | 20/20 | 已知问题修复后的定向回归 |
| Excel R01 | 9/10 | 5/10 | 16/25 | 170/179 | 真实需求完整链路，含失败后恢复 |
| PPT R01 | 10/10 | 7/10 | 36/39 | 602/602 | 真实需求完整链路，含内容和配色返工 |
| Excel R02，重测 R01 中五例 | 5/5 有最终成功交付回执 | 3/5 | 11/15 | 172/175 | XE03 绕过隔离；XE10 会话中断后后台完成，无正常最终 Agent 汇报 |

Excel/PPT R01 合计最终交付 **19/20（95%）**，所有提交 **52/64（81.25%）**，已产生的 Action Response **772/781（98.85%）**。PE05 的一次入口拒绝没有 taskId，必须计入提交分母；否则会误报为 52/63。R02 同理，14 个已准入 Task 之外还有 XE10 一次入口拒绝。

### 按 Task 补齐 Word 主体及复测

Word 已测试 **20 个场景**，四例是其中的问题用例复测。不能因主表突出复测结果而把全部 Word 测试描述为只有四例。按归档原始回执中的唯一 taskId 去重核对：

| Agent 批次 | 受理 Task | succeeded | failed | unknown |
| --- | ---: | ---: | ---: | ---: |
| Word 首轮 20 场景 | 32 | 28 | 2 | 2 |
| Word 四场景复测 | 4 | 4 | 0 | 0 |
| Excel/PPT R01，20 场景 | 63 | 52 | 6 | 5 |
| Excel R02，五场景复测 | 14 | 11 | 2 | 1 |
| 合计 | **113** | **95** | **10** | **8** |

这是 40 个独立场景、49 次场景运行对应的实际 Task 规模；另有两次入口拒绝，纳入提交身份计数为 115。Task 回执成功为 95/113（84.07%），含拒绝的提交成功为 95/115（82.61%）。这些跨迭代统计用于保留执行历史，不宣称统一最终版本成功率。Word 首轮的前置条件问题仍按下文保留，不抹去该批真实执行记录。计数来源与每个 Task ID 见 [Task 审计](../../build/evidence/agent-design-synthesis-20260919/task-count-audit.json)。

全 Action 固定 JSON 批次的 29 个正常成功 Task 属于另一个执行端子集，同批还有两个预期失败 Task；不能拿 29 代表上述 Agent Task 总数。今日机制实验中的夹具、候选、故障注入和重复查询也不能不加区分地计入 Agent 成功率。

“全程无非成功提交”也不等于首次内容正确。PPT 有 Action 全成功但页面目标或颜色不符、随后返工的用例。正常的“先阅读、再新 Task 修改”属于多阶段编排，不是失败后重试。未执行步骤不伪记为失败 Action。

Word 另有旧 20 会话记录，最终输出回执 20/20，但路径占位符未展开、部分前置条件无效，用户已明确不作为正式验收。不能用四例新成功替换旧失败，再拼成新版 20/20。R02 是重复场景，也不能与 R01 当成独立任务集合合并。各批包版本、任务难度和并发条件不同，因此不计算三应用一个总成功率。

原始记录中的人工粗审仍为 pending；本次没有新的人工结论，不将此前执行层三阶段的人工通过迁移到 Agent 批次。

## 2. 按任务达成、效率、安全解释

### 任务达成：能力已证明，验收口径要分开

已有证据支持“Agent 通过这些 Skill 能真实操作离线 WPS 并交付文档”，覆盖 Word 长文、表格与 DOCX/PDF，Excel 数据/公式/工作表操作，PPT 多页文稿等具体任务。它不是只会生成 JSON，也不是只有脚本执行成功。

Word Q4 第二轮还提供更具体的内容证据：Agent 先读取未知正文，原只读 Task 资源释放后，按正文选择符合条件的方案，再以新 Task 重新定位、修改并保存。两次提交、六个 Action 均成功；评估方核对最终 DOCX 的结论事实、其余六段和随机复核码。它证明该样本能跨 Task 使用已返回正文，不能推出整个宿主沙箱或长对话长期保活。[Q4 第二轮](../reports/word/WPS_WORD_Q4_WORKBUDDY_R2_RESULTS.md)

尚未确认的全面内容/视觉验收、当前最终包同条件的完整基线，以及任意任务泛化率，是已有证据的边界，不是“没有做过端到端”。

### 完成效率：已有实际时延，没有整体提速对照

| 历史批次 | 会话全程中位数 | 会话全程累计 | Task 内部累计 | Task 占比 |
| --- | ---: | ---: | ---: | ---: |
| Word 四例 | 35.33 秒 | 221.08 秒 | 27.95 秒 | 12.6% |
| Excel R01 十例 | 179.56 秒 | 2084.80 秒 | 1014.82 秒 | 48.7% |
| PPT R01 十例 | 201.38 秒 | 2281.64 秒 | 619.40 秒 | 27.1% |

Excel/PPT 合计 Task 内部约占 37.4%。统计保留失败、重试、返工时间；会话边界为用户消息至最后可见回复，失败用例的最后回复不能叫成功交付时间。R02 的 XE10 单列：416.2 秒是用户中断时刻，后台最终 Task Response 约在 478.6 秒，不能以中断时刻报告完成速度。

Task 之外包含内容生成、查询 schema、工具调用、路径/编码处理、诊断、预览、记忆写入和最终回复，不能全部称为模型思考。各时间层次嵌套，不能相加。R01 最多 13 个会话时间区间、8 个请求计时重叠，这些数据也不是串行基准。

因此，端到端优化需要同时看执行器和 Agent 的编排、返工、交付成本。今天按需 schema 减少 74.7%–86.8% 输出字节，证明固定选定集合的数据成本；不能直接换算成上述总时间的下降比例。外层 PowerShell 约 95 ms 的夹具启动差异，也不能解释几十秒到数分钟的全部会话成本。

### 操作安全与结果可信：执行端保护有效，Agent 仍可能绕过

昨天 R01 的 XE06/XE08/XE09 有强杀进程、删除或移动隔离记录后继续的证据；R02 的 XE03 实际调用了自建恢复 Skill，随后绕过隔离。这些最终交付不能记作遵守安全边界的成功。PE06 未取得新的用户确认便加入已有修改确认参数，同样属于需审查的 Agent 行为。

今天的受控实验验证了原路径不重放、隔离拒绝、精确绑定和回执事实等执行规则；它不证明拥有其他工具权限的 Agent 无法在系统外部绕过保护。昨天 XE10 还表明“会话中断”不等于后台 Task 已停止，最终结果必须以回执事实为准。

这两天合起来最清楚地说明：**Task/Action Response 用来判断请求执行事实，用户任务验收还必须核对意图、交付内容和执行过程的授权边界。**

## 3. 设计价值如何接到最终目标

| 设计或能力 | 昨天真实 Agent 证据 | 今天或已完成的机制证据 | 支持的价值与边界 |
| --- | --- | --- | --- |
| Application Skill → schema → Task → WPS | 三应用已有自然语言到真实文档的交付记录 | 当前固定请求覆盖全部 85 种 Action | 支持任务可达成；没有“无 Skill”对照，不能量化相对提升 |
| 请求结构与参数语义说明 | Q4 首轮 completion 多填 id 被拒；补齐说明后第二轮 2/2 成功；PPT 颜色说明缺口造成返工 | PPT 查询说明已修复；按需 schema 字节成本已测 | 接口信息影响编排与返工；两个 Q4 样本不构成稳定因果提升比例 |
| 预检、动态引用校验 | 负索引、放错 createWorkbook、错误形状引用被拒绝 | 末尾静态错误的提前/逐步校验对照：零修改对一次部分效果；动态消费者停止 | 减少错误计划造成的损害，不把非法计划变成完成任务 |
| Task 编排与结果引用 | Q4 能先读后理解再提交；其他会话有多步真实编排 | 固定引用链正确；27 个长度样本每 Task 只用一个 bridge | 可执行、资源复用有证据；未测等价逐 Action 接口的端到端提速 |
| 精确绑定与原生回读 | PPT 错页/颜色请求仍可执行成功，提示参数正确性与用户意图有边界 | 切窗口仅改绑定对象；漏写时原生回读检出而乐观候选假成功 | 防止执行偏离已声明目标；不能替 Agent 判断它是否选错页、填错颜色 |
| 提交身份、持久回执、隔离 | R02 重查旧路径返回原回执；会话中断后后台结果仍需查询；实际出现保护被绕过 | 原路径不重放、保存事实保留、超时隔离的断言通过 | 提供安全停止和可诊断事实；不能仅靠提示词保证 Agent 遵守 |
| Excel 读取实现优化与能力组合 | R02 定位 960 格读取超过 60 秒，合并后格式化被拒 | 原生回归 960 格 73.580→9.403 秒，合并后格式化通过 | 直接减少执行成本、消除已复现失败原因；未重测修复后 Agent 总成功率 |

昨天还测过 schema 查询和 Action 拆分，但这两类只到首次生成 JSON，没有执行 WPS，单独归为编排证据。固定 schema 查询样本 6/6 首次 JSON 正确；拆分候选 12/12 静态通过，但实际读取字节反增约 3.35%/18.38%，未显示提速，且配套 Skill 说明不同。不能把这些请求数追加进文档完成率，也不能把正确率差全部归于拆分。[查询实验](../../build/evidence/workbuddy-schema-query-20260918-134716/REPORT.md)、[拆分实验](../../experiments/word-action-split/REPORT.md)

## 4. 当前可以使用的项目结论

> 已在真实 Windows WorkBuddy 中验证 Agent 经 Skill 自主查询能力、编排 Task 并操作 WPS Word/Excel/PPT。历史 Excel/PPT 20 个用例中，19 个取得最终交付成功回执；Word 四个定向回归均首次提交成功。结果仍区分人工验收、失败后返工和保护绕过。后续固定请求验收覆盖全部 85 种 Action，并通过对照实验验证提前校验、精确绑定、原生回读和逐步回执的保护价值；没有将局部成本下降等同于 Agent 端到端提速。

修复后的执行端证据补强了昨天发现问题的解释，但不改写昨天的失败，也不构成一轮新的宿主验收。此报告只综合已有数据；本轮不再复测。
