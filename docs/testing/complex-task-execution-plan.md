# 复杂业务 Task 执行端测试计划：Word / Excel / PPT 各 20 例

日期：2026-09-19。状态：已实现固定请求和断言。早期脚本调试轮次保留；按用户最新要求改为三个独立脚本自动执行，普通失败逐例记录后继续。

## 1. 目标与范围

验证当前执行端能否直接接收固定 Task Request JSON，完成具有业务意义的多步骤操作，返回符合预期的 Task Response 与 Action Response，并记录真实执行耗时。

共 **60 个正常业务用例：Word 20、Excel 20、PPT 20**。每例对应 **一个被测 Task Request**，只操作一个应用的一份独立文档。素材准备可能需要额外 Task，单独标记为 setup，不计入这 60 个业务 Task，也不计入业务耗时。

本轮采用响应断言验收：复用现有执行器内部验证、结果契约校验与测试端预先编写的数据断言。不要求 Agent 参与，不新增视觉验收、外部 OOXML 内容比对、通信压力测试或故障注入。结果只能称为“固定 JSON 复杂任务执行端验收”，不代表真实 Agent 任务完成率或视觉质量。

复杂度来自多项业务操作和真实依赖，而非重复读取凑步数。用例至少覆盖“获取文档 → 多步编辑/结构操作 → 保存或导出”，其中包括内容范围、观察 token、对象 ID 或计算结果引用。具体 Action 数在 JSON 编译完成后逐例记录；受当前 Task 步数上限约束，不预先承诺虚构的步数。

## 2. 三个脚本与复用策略

解压独立测试包后，在 Windows 已登录桌面的终端依次执行：

```powershell
python run_word.py
python run_excel.py
python run_ppt.py
```

每个入口自动新建唯一运行目录，准备素材与请求，顺序执行本应用 20 例并落盘报告；无需逐例手工干预。可用 `--root C:/wps-tests/唯一目录` 指定证据位置。Mac 自动运行时，将三条命令放在同一个交互桌面启动脚本中依次调用，各自返回非零不跳过下一个应用。已有运行目录禁止重放。


- Word：参考已有 20 个业务场景的内容主题，改造成固定素材、固定输入和确定结果的执行端任务；复用 `action_suite.py` 的 Word 响应断言。原 Agent 的写作、理解和自主决策改为预先确定的文本与操作，不使用历史成功结果代替本轮执行。

## 6. 断言与通过标准

### Task Response

每例要求 `type=task.response`、应用匹配、`state=completed`、`outcome=succeeded`、`stop=null`；Task 身份有效，步骤数量与编译后计划完全一致，无缺失、重复、failed、unknown 或 not_executed。`cleanup.outcome=succeeded` 单独检查；执行成功但清理失败仍判本例验收失败，同时保留两项原始状态。

退出码为 0；受理后的提交副本按协议消费；回执查询与首次终态响应的业务事实一致。查询只是读取回执，不重新提交操作。

### Action Response

逐步核对 ID、顺序、Action Address、成功状态以及 Task/trace 身份；用当前正式契约验证每个返回 `data`。每个 Action 至少有业务或身份数据断言，不能只检查 succeeded。

- 文本、矩阵、计数、布尔值、路径和对象身份：精确匹配预先定义的答案。
- 数值与几何：精确计算或明确容差；容差在执行前固定，不因失败临时放宽。
- 引用：确认参数解析自前序返回的对应字段，后续结果达到固定业务答案。预期答案不得通过照抄被测结果生成；动态 ID/token 可以使用返回身份做关联校验。
- 格式和结构：断言正式响应暴露的字段；无法观测的要求不能声称已自动验证。请求实现阶段逐项落到 JSON 字段路径，若现有结果无法支持则明确缩减该要求或增加一次定向读取。
- 保存与导出：核对返回产物路径、格式、正数大小与文档状态；不把 artifact 响应断言描述为独立文件内容验收。

`request.json` 不加入测试专用 checks；预期保存在独立 `expected.json`。Word 不复用已失效范围；Excel/PPT 修改前取得正确观察 token。

**单例通过 = Task 公共断言 + 全部 Action 契约/业务断言 + 清理断言通过。** 整轮通过要求 60/60，不用部分步骤成功代替完整业务任务成功。

3. Windows 使用本轮唯一独立目录。提前生成固定已有文档、图片和中文素材，记录哈希；输入均为副本，输出路径互不覆盖。setup 失败则记录失败，并仅阻塞依赖它的业务用例，不消耗业务用例编号。
4. 记录 Windows、Python、WPS、字体及 WPS 启动状态；只做必要就绪检查，不重复通信实验。Mac 启动 Windows 端批次，Windows 本地持续运行并落盘，Mac 可回连查询。
5. 串行执行 CW01–CW20、CE01–CE20、CP01–CP20，每例一次。通过文件提交 UTF-8 JSON，走正式 Task CLI；不经宿主、不手工粘贴命令行 JSON、不绕过执行器直调 COM。
6. 每个用例内部仍按正式 Task 语义在失败后停止后续 Action。测试批次记录普通断言失败或已终止并清理成功的 Task 失败，保留现场后继续下一个独立用例，不重试、不从头重跑。素材失败只将依赖它的业务用例标记 blocked；其他用例继续。无法确认执行已经结束、超时或资源未释放时停止对应应用，剩余用例明确 not_run；随后仍运行其他独立应用脚本。
7. 成功后由测试工具仅关闭已核验、已保存、精确路径匹配的本轮测试文档，避免累积影响后续样本；不退出 WPS，不关闭用户其他文档。测试工具收尾时间不算 Task 时间。

每例保留：原始请求、提交副本状态、预期、stdout/stderr、Task Response、回执、trace、断言差异、耗时和产物路径。总 manifest 记录上述文件哈希及构建/环境信息。

执行预算沿用已有单例 300 秒观察上限，开始前核对原有 Action/Task 超时配置；超出时停止后续调度并记录 timeout/unknown，不推断没有文档效果，也不强制解除隔离。清理是否完成必须从正式结果核实。

## 8. 数据报告

每例：业务规模、总 Action 次数、不同 Action 数、断言通过/失败、失败步骤和错误、Task 总耗时、逐 Action 耗时、最慢 3 个 Action。

- Task 时间用同次执行 trace 的 `request.total`；Action 时间用 `action.execute`。Action 已包含在 Task 内，不能相加。Task 时间包含内部处理和清理，不含 Agent、解释器启动、夹具准备和测试端断言。
- 若另外记录 Windows 端 CLI 子进程启动至退出的墙钟时间，明确另列，不与 `request.total` 混用。
- 每个应用汇总成功/失败/unknown/not_run 数量；只有 20 例全部执行完成才能报告该应用完整完成率，未执行不能算成功。
- 性能仅汇总正常且全部断言通过的业务 Task，报告样本数、中位数、最小/最大值、总耗时及 Action 次数。慢但成功的样本不能删除。样本是不同工作量的各一次测试，不当作稳定性分布或提速对照实验。
- 预期可形成“60 个复杂业务 Task 执行验收”的证据；实际通过率和速度待测试结果产生后填写，不提前写 100%。不据此声称 Agent 自主完成 60 个场景。

## 9. 本阶段交付与后续

三个入口共享请求生成、正式 CLI 调用和响应断言实现，避免复制三份调度逻辑。下一批固定版本运行完毕后统一分析；执行期间不修改断言，不因某个失败自动重跑整批。历史脚本准备错误与实际产品失败分别归因。
