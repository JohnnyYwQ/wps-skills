## 目标与范围

仅复测 XE03、XE06、XE08、XE09、XE10，顺序固定。观察在不并发、不允许 Agent 清理隔离或强杀进程的条件下，是否仍出现读取超时、RPC 失败，以及最终交付能否完成。PPT 的参数、引用及配色问题另立验证，不混入本轮。

- Windows 使用已登录交互桌面。每例工作目录由宿主侧配置并记录；若宿主使用自己的会话目录，记录实际路径，不冒充已切换到 cases 目录。

## 串行操作流程与停止条件

1. 每次只发送一条，顺序 XE03 → XE06 → XE08 → XE09 → XE10。不在其他新对话同时运行 Office 任务。
2. 正常结束需同时满足：Agent 最终回复已出现、没有后台工具继续执行、所有已提交 Task 回执为终态、cleanup 成功且没有待处理的隔离/未知状态。仅看到文件生成或某个 Task succeeded，不等于本例已经结束。
3. 正常结束后，保存会话标识与回执，再开下一例。可在五例运行完毕后集中人工粗审，避免运行中手动编辑测试文档。
4. 发现 failed、unknown、rejected 或 cleanup 失败时，**暂停整轮，先收集现场**；不发送“继续”“修复一下”或同一请求，不自行加超时、清理协调文件、强杀进程。下一例须等维护分析确认环境可继续后再开，不把暂停后的等待计入下一例耗时。
5. 若 Agent 自行开始重试、清理记录或杀进程，先停止该会话继续规划，保留已执行命令和回执；停止宿主会话不等于底层 WPS 已停止，仍需检查后台状态。该例标记流程违规，不删除失败、不用最终成功覆盖。
6. 每例观察上限 10 分钟；超过时标记超时待确认并暂停，不直接认定所有动作均未生效。
7. 串行性用日志复核：本例全部执行结束必须早于下一例提交。发生重叠则保留该次为污染样本，另开新路径复测，不悄悄剔除。

## 成功条件与取证

**单例结果分三栏，不能互相替代：**

- 回执结果：实现用户目标的文档操作与所需保存/导出均有 succeeded Task Response；完整保留所有提交及失败。Task 全成功但漏编排用户要求时，不能凭回执宣称内容达标。
- 流程结果：没有失败后自动重试、绕过保护、强杀进程、擅自写恢复 Skill；正常先读后改不算重试。
- 人工粗审：依据每例效果说明判断内容与布局，用户明确反馈前一律 pending。

记录每个 Task 的文档获取、step、completion 和 cleanup；错误至少包含 taskId、stepId、Action 名、error code、phase、后续未执行步骤。不只看顶层 outcome。回执查询不是重试，但重新提交修改后的请求必须计为新提交。

计时保留：用户消息 T0、首次提交 T1、最终交付 Task Response T2、最终回复 T3；另记全部后续验证 Task 返回时刻。报告端到端 T3−T0、所有 request.total、每个 action.execute、bridge.round_trip；通信估算仅对能匹配 bridgeRequestId+operation+时间窗口的原生计时计算，标注缺失样本和嵌套关系，不把 WPS 等待时间当纯通信。人工介入和暂停时间单独记。

若再现超时或 RPC：额外保留目标文档的真实 WPS 进程关联、进程退出/结束时间、当前未结束请求、协调状态副本及最后桥接日志。只观察，不由 Agent 修复，用于判断进程干扰还是独立阻塞。
