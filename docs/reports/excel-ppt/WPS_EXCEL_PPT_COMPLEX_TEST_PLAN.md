## 初始条件与执行顺序

Windows 根目录已写为 `C:/Users/yim/wps-complex-plan-20260918-r01`，无 ROOT 占位符。实测前由测试准备流程部署当前安装包、样例图片、请求与输出父目录；记录包版本、Windows/WPS 版本、字体和启动状态。目录准备在计时前完成，执行中不得补建缺失目录以掩盖失败。

每个正常新建用例使用独立文档和唯一输出路径。X10、P10 先执行对应 setup，确认保存回执达标后再提交正式请求；准备失败则记为阻塞，不能换用其他已有文件。两例保护场景会留下未保存文档，测试后单独清理本轮文档，清理不计入任务时间，不处置用户文档。

启动前必须检查测试进程处于已登录用户的交互桌面（Session ID 非 0），不能从 SSH Session 0 直接调用 WPS。记录解释器实际版本，不能依据安装目录名称判断。逐个串行提交，一次只运行一个 Task；保留提交前 JSON 副本，因为输入文件可能被消费。Action 超时沿用 60 秒。遇到失败记录当前响应及停止位置，不修参数后覆盖首次结果，也不把重跑当首次通过；如需修复验证，应新建轮次目录并保留两轮证据。

## 响应判定

正常场景须同时满足：Task 为 completed/succeeded；计划中的 Action 均成功；逐步响应里的关键内容、格式、路径、状态符合预期；清理成功。保存和导出按 Action 内置回读证明及响应判断，不另加一套文件解析或验证 Task。

保护场景须满足：指定步骤返回指定错误，Task 为 stopped/failed，前序步骤成功、后续步骤 not_executed。这属于“保护用例通过”，不属于“Task 成功”。错误步骤或错误码不符，即使同样失败也不能通过。

TaskId、traceId、token、形状 ID 等运行时值不硬编码；按非空、身份关联和前序响应引用比对。数值容差写入对应断言，不能实测后为通过而放宽。合并区域先设格式再合并；公式错误单元格检查公式、空 value 和非空 errorCode，不硬编码 COM 错误码的整数表示。

区分三种问题：① Task/Action 明确失败；② Action 报成功但关键返回值与预期不符；③ 响应达标但人工粗审发现效果问题。第二种不改写原始 Action outcome，单列响应断言差异。

已有离线响应比对器 `src/test/python/tests/applications/response_expectations.py` 可检查每步预期；正式执行还需归档原始 stdout、持久回执及 trace，比较 stdout 与回执的业务结果，单列仅提交入口返回的字段。人工粗审按清单逐项记录通过、问题或未审，不由自动通过代替。

## 时间记录与分析

每次提交同时保留 Windows 本机进程外侧墙钟时间、内部 `request.total`、每个 Action 的 `action.execute` 和细分 trace。外侧计时从启动本次请求调用到收齐响应，内部计时覆盖 JSON 读入到响应写出；SSH 传输、文件部署、准备任务、人工审核分别统计，不混入执行时间。

逐 Task 记录：输入读取/解码、校验、准入及锁等待、执行资源启动、Action 执行、回执写入、清理、响应编码与输出，以及整体耗时。逐 Action 记录 stepId、名称、结果、错误码、执行毫秒数及关联 traceId。

通信细分以实际 trace 为准，展示请求编码/写入、等待返回、响应解码及 bridge 往返时间；**bridge 往返包含 WPS 执行，等待返回也不等于纯通信耗时**。能够配对的原生执行跨度可用于解释开销，其余标为等待或未归因，不能全称为通信。不同进程只比较各自单调时钟算出的时长，不直接相减时间戳；嵌套 span 不重复相加。

报告每例总耗时、每个 Action 耗时，按应用和 Action 名称汇总样本数、总量、中位数、P95、最大值及最慢步骤。样本很少时以原始值为主，启动/打开与内容操作分开分析；本轮不预设未经测量的性能合格线，也不把一次样本称为稳定性能。

正式执行后产出原始响应与 trace，以及 tasks.csv、actions.csv、timings.csv、assertions.csv 和人工审核清单；这些实测结果目前尚未生成。
