2. 在 Windows 已登录交互桌面使用 WorkBuddy，每例新建独立会话，通过宿主技能选择入口显式选择 `wps-excel` 或 `wps-ppt`。模型固定为此前指定的 `deepseekv4.1 flash`，记录界面实际显示名称及可见模型标识；不存在该选项时暂停，不自行换模型。

4. Agent 自己读 Skill、选择操作、查 schema、编排 JSON、提交、理解回执并汇报。可以为理解已有内容先做只读 Task，再做修改 Task；不预设 Task/Action 的数量和顺序，不提供标准 JSON。

- 在 `input` 放置下文明确的独立副本，在 `output` 预建输出父目录；正常用例的输出目标初始不存在。每例宿主工作目录设为 `cases/用例编号`，请求与日志互不复用。

- 统一检查字体（宋体、黑体、Arial）、图片、输入内容、文件权限、宿主 Skill 选择和输出目录。记录 WPS、WorkBuddy、实际 Python 版本和执行会话；确认真实 WPS 调用位于交互桌面，避免之前 SSH Session 0 的测试入口问题。

## 成功标准

**自动通过**：达成用户要求所需的全部 Task Response 均 `completed/succeeded`，没有拒绝、失败或 unknown，所请求交付在回执中有成功的保存/导出结果。多 Task 逐个核对。没有提交、只有读取就宣称已修改、漏掉指定交付、只有 Agent 口头说成功，都不能算自动通过。

**人工通过**：你根据每例自然语言审核点查看内容、排版与实际文件，确认基本达标。端到端通过须同时满足自动通过与人工通过；未审始终标为待审。

默认信任 Action 内置回读，不额外解析 XLSX/PPTX、比对截图或派发验证 Task。Action Response 用来追踪已完成步骤、具体失败位置与错误；下方期望数值是人工粗审依据，不注入 Agent 的请求。保存/导出路径以 Task Response 为准。

本轮不自动修复再提交。若 Agent 自行失败后重试，保留首次失败和全部后续请求，单列“违反停止规则”，不能用最终文件成功掩盖首次失败。需要修复时新建轮次和副本；原结果保留。schema 查询分批补齐和成功的只读 Task 后继续编辑不属于失败重试。

## 指标与计时

| 指标 | 统计口径 |
| --- | --- |
| 自动任务完成率 | 自动通过的用户用例 / 已启动用例；同时列计划20例、未启动与准备阻塞数 |
| 人工粗审通过率 | 人工通过 / 已审核，另列待审 |
| 端到端完成率 | 自动且人工通过 / 已启动用例；结果全部收齐后再给最终值 |
| Task 成功率 | succeeded / 已提交 Task；rejected、failed、unknown 分列，只读 Task 成功不替代用户任务成功 |
| Action 成功率 | succeeded / 已执行 Action；failed、unknown、not_executed 分列，未执行不进已执行分母 |
| 非法调用比例 | 契约/参数/引用校验拒绝次数 / 全部 Task 提交尝试；不把环境错误或正常业务保护当参数错误 |
| 交互与流程 | 澄清、schema 查询次数与截断、额外验证性回读、失败后重试、工具绕路、最终错误汇报是否真实 |

只采公开消息、工具调用、JSON、Task Response 和 trace，不采模型内部推理。记录模型设置、提示词、首次提交和每次回执时间；无法取得的阶段计时明确标缺失，不按零处理。

- T0：提示词提交；T1：第一个 Task 开始提交；T2：最后一个必要 Task Response 返回；T3：Agent 最终汇报完成。
- 每例报告 T1−T0（首次编排）、T2−T0（到执行结束）、T3−T0（完整端到端）、T3−T2（尾部汇报）。多 Task 单列各次回执到下次提交的间隔，不把它全称为模型推理时间。
- 每个 Task 记录 JSON 读入至响应写出的 `request.total`、每个 `action.execute`、输入与参数处理、资源启动、清理、响应输出及 bridge 阶段。
- bridge 往返和等待包含原生执行，不能称作纯通信；分别展示编码、写入、解码及 native.operation。跨进程以各自时长、匹配的 operation 比较，不直接相减不同单调时钟时间戳，不重复相加嵌套跨度。
- 各应用分别报告每例、成功例中位数和最大值，必要时按新建/先读后改/复杂交付分类；失败的停止耗时单列，不用失败较早的短时间改善成功任务平均值。首轮每例一次，样本不支持稳定性或长期P95结论。
