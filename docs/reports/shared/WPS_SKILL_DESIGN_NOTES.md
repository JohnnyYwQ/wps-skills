## 1. 项目背景

原始要求是：基于给定的 WPS Skills 仓库，移除 MCP，并接入内网智能体。

移除 MCP 的具体原因尚未确认，不能把“内网环境必须移除 MCP”作为已成立的技术依据。当前暂不讨论内网平台的接入条件，假设目标智能体能够读取 `SKILL.md`，并通过本地命令执行工具运行 Skill 附带的程序。

`SKILL.md` 提供能力发现和程序使用指引；Task Orchestrator 根据指引，通过其命令执行工具启动程序。说明文档本身不执行操作。

开发时主要参考了原方案使用 WPS COM 的部分。文档绑定、Session、内容 token、Lease 和执行后回读等机制是在重新设计过程中引入的。

第一阶段优先支持 Windows。macOS 和 Linux 是后续方向，不属于当前验收范围。当前执行路径的可行性不能直接外推为跨平台可行性。

## 2. 目标场景与体验

希望 Task Orchestrator 能根据用户请求，在真实、可见的 WPS 窗口中完成文档操作。以 WPS 文字中的作文任务为首个具体场景：

- 新建文档：用户要求写一篇关于考试的小作文，Agent 新建文档、写入作文并保存。
- 修改已有文档：Agent 打开用户指定的已有文档，按要求修改，并根据保存授权处理结果。
- 可见性：用户可以看到 WPS 文档窗口及写入后的内容；允许一次性写入整篇作文，不要求逐字或逐段展示。

“在真实 WPS 窗口中看到内容变化”来自产品设想，目前尚未验证用户是否需要或偏好这种体验。

职责划分：

- Task Orchestrator 负责理解用户请求、生成内容、规划 Action、处理必要的用户确认，以及判断整个 WPS Task 是否完成。
- Application Skill 提供应用操作指引和能力契约，附带程序支持实际文档操作及执行反馈。

### 本次讨论中的保存要求

- 已有文档的保存需要用户授权。
- 用户最初的请求明确包含“保存”时，视为已授权，无需为同一授权重复确认。
- 没有明确保存授权时，在保存前询问。
- 如果目标文档已有未保存的用户修改，需要在第一次修改前说明这些修改也会一起保存，并取得确认；已有明确授权时沿用授权。

其中，“没有明确保存授权时询问”与现有领域文档中“修改已有文件默认显式保存”的规则不同，属于待协调的需求差异。本文保留讨论结果，尚未修改现有 ADR 或实现。

### 任务成功的最终定义（历史讨论，时间门槛已由第 7.5 节更新）

本次讨论将任务成功定义为同时满足以下三个条件，除此之外不再增加独立的成功门槛：

1. **完成用户预期**：最终结果符合用户要求，包括适用的保存授权与交付要求。
2. **没有打开多余文档**：只新建或打开任务需要的目标文档，不因重复调用、重试等原因产生额外文档或重复窗口。用户原本打开的其他文档不计入，也不能为满足数量要求而关闭它们。
3. **10 秒内出现可见进展**：从 Agent 开始加载本 Skill 起，到目标 WPS 文档窗口可见且出现本次任务相关的实际内容，耗时不超过 10 秒。

第三项称为“首次可见进展时间”，按以下条件验收：

- Skill 已安装、运行环境已配置好，WPS 应用原本未运行；安装与环境配置时间不计入。
- 计时从开始加载 Skill 算起，不从读完 `SKILL.md` 或首次调用底层 WPS 程序算起。加载指引、发现能力、准备内容和参数、启动 WPS、新建或打开文档以及首次写入均计入。
- 写入与任务相关的标题即可达标，不要求正文或保存也在 10 秒内完成。只打开空白窗口，或仅由 Agent 提示“正在处理”，不算可见进展。
- 允许一次性写入完整内容，也允许先写标题再继续正文；不要求逐字或逐段展示。
- 以智能体服务正常可用为前提，固定模型、环境和测试任务；正常的思考、工具调用与网络波动计入耗时。明确的服务故障单独记录，不能因为一次运行慢就将其归为异常并排除。

10 秒目前是待验证的硬门槛。超过 10 秒仍无可见进展，即使最终完成用户要求，本次任务验收仍失败；记录时区分“最终结果完成”和“首次进展超时”，便于判断失败原因。

整个任务暂不设统一完成时限，因为任务量不同。出现部分内容只代表首次进展达标，仍需最终完成用户预期。中途某个 Action 因参数错误等原因失败，但被正确修复且最终满足上述三项时，整次任务仍算成功。

这些是本项目的整体任务验收条件，不改变现有领域模型中 Task Outcome、Action Response 与 Session Outcome 的含义。下文的绑定、检查、回读等是支撑目标的设计手段，其机制验证不额外增加整体任务成功条件。

## 3. 已有观察与证据边界

目前有以下经历，需要分别记录，不能默认它们具有相同原因：

1. 在 WorkBuddy 上试用过参考方案，主观感受是整体执行较慢；WPS 打开后，内容写入较快。未保留足够的分段耗时和中间调用记录，无法确认瓶颈位置。
2. 曾直接模拟 Agent 指令执行部分操作，速度尚可。这不是完整的真实 Agent 端到端评测。
3. 曾在某一版实现中观察到 PowerShell 反复启动、关闭耗时较多，使多步任务变慢。这为 Session 复用提供了直接动机，但收益尚未量化。
4. 参考方案根据当前活动文档选择写入目标。这存在目标随活动窗口变化的风险，但本次讨论未确认实际误写其他文档的案例。
5. 早期 HTTP 桥接版本的监听进程持续运行，修改代码后执行仍持续返回 `unknown`。停止旧监听进程并重新启动后，现象消失。这支持问题与旧进程保留的代码或运行状态有关，但未定位具体原因，也不能据此认定 HTTP 本身存在问题。
6. 曾遇到 Agent 参数构造问题，也在其他仓库中看到输入校验实现；具体错误案例尚未整理。
7. 曾尝试 WPS JavaScript 加载项方案，在 Windows 上遇到编码问题。具体错误位置和原因尚未确认，不能据此认定该技术路线不可行。
8. 曾亲自通过 PowerShell 成功调用 WPS COM，随后继续沿用。选择 Python 的依据是目标环境支持 Python，且开发者相对熟悉；没有进行系统的语言或桥接方案比较。

当前这套 Skill 尚未经过真实 Agent 的端到端试用。仓库已有实现层测试和部分原生验收记录，不应写成“完全没有测试”；当前缺口是真实 Agent 从自然语言请求开始的完整任务评测。

## 4. 九个设计点

| 设计点 | 要解决的问题 | 当前依据 |
| --- | --- | --- |
| Session Document Binding | 操作目标随活动窗口变化 | 参考方案使用活动文档作为目标 |
| Action Session | 重复启动耗时，以及跨会话遗留进程和状态 | 观察过重复启动耗时及旧监听进程重启后恢复 |
| 内容 token / Content Revision 检查 | Agent 基于过期内容写入，覆盖用户新修改 | 针对并发编辑风险的设计，尚未系统验证 |
| Document Lease | 多个自动化会话交错操作同一文档 | 借鉴其他实现的预防措施 |
| 执行后回读 | 调用未报错，但实际效果缺少确认 | 预防性设计，相关故障记忆尚未核实 |
| Action 封装 | Agent 需要处理较多底层调用和检查细节 | 封装内容可从实现确认，降低决策和上下文负担仍是假设 |
| Runtime 参数校验 | 错误请求进入应用执行层 | 曾遇到参数问题，并参考过其他实现 |
| 不确定结果处理 | 修改可能部分生效，直接重试可能重复写入或覆盖用户修改 | 已确认的交互与执行策略，待验证 |
| WPS 操作路径与实现语言选型 | 在现有环境和开发条件下先完成 Windows 版本 | PowerShell COM 已调用成功，环境支持且开发者熟悉 Python |

### 4.1 文档绑定：始终操作指定文档

**问题与动机**：参考方案向当前活动文档写入。用户切换窗口后，后续操作可能落到另一份文档。引入绑定的主要目的，是避免操作目标随活动窗口变化。

**设计要求**：建立 Session Document Binding 后，后续文档 Action 始终操作该确切文档；无法继续确认绑定身份时，停止并报告，不跟随新的活动窗口。

**保证边界**：保证操作目标不随活动窗口变化，不保证文档内容不变，也不阻止用户编辑。

**待验证**：绑定文档 A 后，将文档 B 切为活动窗口，确认修改仍作用于 A，B 未被修改。

### 4.2 Action Session：复用资源并管理生命周期

**问题与动机**：此前某一版实现反复启动、关闭 PowerShell，导致任务明显变慢。另一版 HTTP 桥接曾出现旧监听进程持续运行、改代码后执行仍持续返回 `unknown` 的情况，停止旧进程并重启后恢复。两次经历分别支持减少重复启动和明确进程生命周期，不能混为同一故障。

**设计要求**：在一个应用范围的 Action Session 内，复用 PowerShell 桥接进程、WPS 连接和绑定的文档对象；明确资源的所有者、复用范围和结束条件。Session 结束时有界清理其拥有的自动化资源并报告结果，后续 Session 重新创建自己的资源。

**预期收益**：会话内复用以减少重复初始化和清理开销；会话间释放以限制旧进程及遗留状态干扰后续运行。具体效果尚未量化。

**职责边界**：

- 文档绑定回答“后续操作哪份文档”。
- Action Session 回答“执行资源复用多久、由谁管理”。
- Session 清理不负责保存或关闭用户的 WPS 文档；Task Outcome 与 Session Outcome 分别判断。
- PowerShell 反复启动很慢，不足以证明 PowerShell 本身不适合作为桥接实现。
- HTTP 服务持续监听本身不一定是故障；问题在于生命周期是否符合预期，以及代码更新如何生效。
- Session 不会自动热更新代码；修改代码后，已运行的 Session 需要结束并重新启动。生命周期管理也不能消除所有 `unknown`。
- 清理对象是 Session 拥有的桥接进程等自动化资源，不是用户的 WPS 应用或文档。桥接退出不等于已提交给 WPS 的操作必然停止，无法证明停止时遵守 Document Quarantine 规则。

**待验证**：记录启动、首个 Action、后续 Action 和清理耗时，在相同操作与环境下评估复用收益；检查正常结束和异常中断后的资源状态，以及后续 Session 是否独立使用新进程和代码。

### 4.3 内容状态检查：发现修改依据已经过期

**问题与动机**：Agent 读取内容后、写入前，用户可能修改同一处内容。按旧观察直接写入，可能覆盖用户的新修改。

**设计要求**：写入前检查相关内容的观察状态。发现变化时，拒绝该次旧请求；由 Task Orchestrator 重新读取、说明冲突，并询问用户如何处理。

**机制与边界**：

- 各应用使用自己的观察机制，例如 Excel/PPT 的内容 token、Word 的 Content Revision；不假定它们具有相同的覆盖范围或契约。
- 状态检查负责发现变化；Task Orchestrator 负责理解变化并与用户交互。
- 用户同意覆盖后，也应基于最新观察重新判断并发起修改，不绕过检查提交旧请求。
- 必须明确检查覆盖的内容、结构、属性和检查时机；不能据此声称整个读写过程具有事务隔离。

**待验证**：读取后人工修改同一区域，再提交旧观察状态对应的写入，确认请求被拒绝且用户修改保留。

### 4.4 Document Lease：防止多个自动化会话相互干扰

**问题与动机**：多个 Action Session 同时访问同一文档时，观察和修改可能交错，影响结果判断。当前主要场景是单会话，Lease 来自对其他实现的借鉴，用于防止意外重复启动等情况产生多个会话。

**设计要求**：同一文档同一时间只允许一个 Action Session 访问，包括读取和修改；其他会话的访问被拒绝，不自动排队或重试。

**取舍与边界**：

- 独占 Lease 是简化并发处理的一种选择，不代表所有并发读写都不可实现。
- 代价是其他会话即使只想读取，也不能同时访问该文档。
- Lease 约束遵守协调机制的自动化会话，不阻止用户直接编辑，因此仍需要内容状态检查。
- 当前属于防御性约束，其必要性尚未通过实际多会话使用评估。
- 正常释放与异常中断需要区分；无法证明在途 WPS 操作已经停止时，现有模型通过 Document Quarantine 保留限制，不能立即重新取得 Lease。

**待验证**：两个会话尝试访问同一文档，确认第二个被拒绝；正常释放后可以重新取得 Lease；异常中断按是否能证明操作停止分别验证处理结果。

### 4.5 执行后回读：为成功响应提供实际状态依据

**问题与动机**：主要为了预防“调用没有报错，但实际修改不符合预期”。对类似故障有模糊记忆，但目前没有已确认、可复现的案例，不作为已发生故障记录。

**设计要求**：修改后读取相关文档状态，与 Action 契约规定的预期结果比较。无法确认完整效果时，不报告已验证成功；可能已经发生修改时，按 Uncertain Outcome 处理，不自动重放。

**保证边界**：

- 回读只能证明检查过的后置条件，例如文字正确不代表排版也正确。
- 单个 Action 成功不等于整个 WPS Task 完成，也不等于已按要求保存。
- 最终任务验收仍需对照用户要求和 Persistence Intent。
- 回读会增加执行开销，需要与其检错价值一起评估。

**待验证**：检查回读能否识别未生效、部分生效或结果不匹配的情况，并记录额外耗时。

### 4.6 Action 封装：让 Agent 决定目标，程序处理执行细节

**问题与动机**：直接操作细粒度 WPS COM 接口，可能要求 Agent 选择和组合较多底层调用，增加规划负担和所需上下文。这是开发者的直觉，尚未通过对照评测证明。

**设计要求**：Task Orchestrator 决定修改位置、内容、操作顺序及是否按授权保存；程序按 Action Contract 执行，检查前置条件并验证实际结果。重复的 COM 调用细节、检查和回读集中在程序中。

**已检查的实现例子**：Excel 的 `writeRange` 包含写前读取、区域可编辑性和 token 检查、数据写入及写后回读，并通过返回值校验检查实际值。它不包含保存，`save` 是独立 Action。Agent 仍需先用 `readRange` 获取观察 token，再提交工作表、区域、数据和 `expectedToken`。

实现依据：[区域操作](../../../src/main/resources/wps_skills/excel/windows/excel_actions.ps1)、[Action 契约及结果校验](../../../src/main/python/wps_skills/excel/contracts.py)。具体代码由 Codex 实现，讨论中通过阅读代码确认了上述边界，不能将未审阅的细节写成开发者已经掌握或验证的事实。

**取舍与证据边界**：

- 封装固定了一部分操作步骤，同时限制 Agent 自由组合底层能力的空间。
- Action 应围绕清楚、可验证的操作划分，不以合并步骤数量最多为目标。保存涉及独立的授权判断，因此保持独立。
- COM 接口细粒度高，不必然意味着上下文大；实际还取决于加载方式、查询轮数、示例和参数复杂度。
- 已能确认程序隐藏了部分底层细节；是否降低 Agent 决策难度、上下文消耗或任务耗时，仍需验证。

**待验证**：用真实 Agent 完成相同任务，观察能力选择、参数修正、工具调用轮数、上下文用量及最终结果，再评估当前 Action 粒度。

### 4.7 Runtime 参数校验：拒绝非法请求，默认值遵守契约

**问题与动机**：曾遇到 Agent 构造参数的问题，也参考过其他仓库的输入校验。Skill 说明规则不等于调用方每次都能遵守，Action Request 必须作为外部、不可信输入处理。

**设计要求**：非法请求在进入应用执行层前被拒绝，返回具体字段和预期要求，由 Agent 修正。仅对契约明确声明的可选参数使用默认值，不靠猜测修正请求。

| 情况 | 处理规则 |
| --- | --- |
| 省略可选参数，且契约明确规定默认值 | 应用公开的默认值 |
| 缺少必填参数 | 返回错误，由 Agent 补充 |
| 参数类型、范围或组合不合法 | 返回错误，由 Agent 修正 |
| 修改目标、写入内容、覆盖或保存授权不明确 | 不推断、不自动补齐 |

例如，列表查询的分页大小可以有契约规定的默认值；`writeRange` 的矩阵尺寸与区域不一致时，应拒绝而非截断或补空值。默认值是接口事先约定的行为，不等于自动纠错。

**职责边界**：

- 参数校验检查请求是否符合契约，如必填字段、类型、范围和矩阵尺寸。
- 文档绑定、保护状态、观察状态是否过期等属于执行前提检查；回读属于执行结果验证。
- 参数合法不代表符合用户意图。用户要改 A1，但 Agent 提交合法的 B1，普通参数校验无法识别此类意图错误。

**证据状态与待验证**：上述规则已在讨论中确认，当前实现是否完全符合仍需逐项检查。验证非法请求未进入应用执行层、错误反馈足以支持修正，以及默认值行为符合公开契约。

### 4.8 不确定结果处理：先核实，部分完成后询问用户

**问题与动机**：写入返回 `unknown` 或响应丢失时，修改可能未发生、全部发生或部分发生。中断后用户可能已经接手编辑，直接重放原请求可能重复写入或覆盖新内容。

**设计要求**：任务仍在继续或用户要求恢复时，在能够安全读取原文档的条件下，先通过只读操作核实当前状态；不自动重试原写入。确认只完成一部分时，说明已确认的结果和剩余内容，取得用户确认后再继续修改。

**执行与交互边界**：

- 检查修改位置、内容和效果是否符合预期，不只统计写入数量；当前内容符合预期也不一定能证明是 Agent 写入的。
- 预期修改已全部存在时，可据此继续任务剩余步骤；仍无法确认时，保留 Uncertain Outcome 并向用户说明。
- 原操作可能仍在执行，或 Session 已不可用时，不能立即继续读取或另开会话绕过限制；先满足现有绑定、生命周期和 Document Quarantine 规则，否则停止并报告。
- 用户已明确要求停止时，Agent 应停止，不自行继续检查。后续核实需要用户恢复任务或另行提出要求。
- 用户同意继续部分完成的任务后，基于最新观察重新规划，不盲目重放旧请求；确认内容可能包含用户在中断后的修改。

**职责区分**：执行后回读是程序对单次 Action 的验证；不确定结果处理是 Task Orchestrator 在无法取得确定结果时如何继续。部分完成后先询问用户是本次确认的交互要求，实现和 Skill 指引是否完整体现仍待核对。

**待验证**：覆盖部分写入、响应丢失和中断后用户编辑的情形，确认先只读核实，部分完成时先询问，并且不在用户停止后擅自继续操作。

### 4.9 WPS 操作路径与实现语言：先完成 Windows 版本

**阶段范围**：优先支持 Windows，macOS 和 Linux 留待后续，不要求当前执行路径直接覆盖其他平台。

**尝试过的路线**：

- JavaScript 加载项路线：Agent → Python → 本机 HTTP → WPS JavaScript 加载项 → 文档。
- 当前路线：Agent → Python Runtime → PowerShell → WPS COM → 文档。

讨论中检查了 `JohnnyYwQ/wps-skills-py` 的 `main` 当时对应提交 `eac5008af6d86e17c4d1c791191ae549e4b3c5c5`。其 [ADR 0005](https://github.com/JohnnyYwQ/wps-skills-py/blob/eac5008af6d86e17c4d1c791191ae549e4b3c5c5/docs/adr/0005-use-one-wps-js-bridge-on-all-targets.md) 和 [README](https://github.com/JohnnyYwQ/wps-skills-py/blob/eac5008af6d86e17c4d1c791191ae549e4b3c5c5/README.md) 明确采用 WPS 托管的 JavaScript 加载项与本机回环通信，并停用 Windows PowerShell COM 路径。该提交不一定与此前出现编码问题的版本完全相同。

**当前选择的依据**：

- 参考方案展示过 WPS COM 可以操作真实 WPS。
- 开发者曾用 PowerShell 成功调用 COM，因此继续使用这一已跑通的方式；不是仅因参考方案采用 PowerShell 而照搬。
- 目标环境支持 Python，开发者也相对熟悉，因此用 Python 承载调用入口和 Runtime。
- 此前尝试 JavaScript 加载项路线时遇到 Windows 编码问题，但未明确定位原因，也未系统比较不同路线。

**接受的代价与证据边界**：当前执行路径依赖 Windows；后续平台需要重新选择并验证执行方式。这是依据环境条件、个人熟悉度和已有可运行经验作出的阶段性取舍，不代表 COM 是唯一或全面最优的路线，也不代表 Python 或 PowerShell 已被证明优于其他语言。某次实现中的编码错误不能作为整条技术路线不可行的证据。

**待验证**：先验证当前 Windows 路径能否达到整体任务成功条件。性能需要拆分耗时后再判断是否值得替换桥接；后续平台选型另行验证，不提前声称已具备兼容性。

### 7.3 当前应怎样验证设计

先把每个设计点写成“要解决的问题 → 可检验的假设 → 方法 → 证据 → 结论”，优先补当前证据缺口。机制正确性与收益有效性分别判断：同一 Session 确实复用进程，不等于已证明它显著降低整个 Agent 任务耗时；成功生成文档也不证明绑定、Lease 或过期内容检查能拦住风险。

### 8.2 从原问题到可观察结果

原问题是 Task Orchestrator 缺少能力发现、绑定真实文档和取得可验证执行反馈的机制。评价应分别回答“机制是否正确”“Agent 是否用得好”“最终是否完成用户任务”，不能用一项总通过率代替三者。

| 要评价的问题 | 记录什么、怎样判断 | 关联设计与所需测试 |
| --- | --- | --- |
| 能否发现能力并正确调用 | 记录首次执行请求是否合法、选用的 Actions 是否适合用户要求、为纠正请求产生的额外往返；schema 获取次数与可见的读取量另记 | D06/D07/D11/D12；真实 WorkBuddy 测试。脚本预先写对 JSON 不能证明 Agent 能正确发现和使用 |
| 是否始终操作指定文档 | 焦点切换确实发生后，目标修改符合预期，非目标文档没有被修改；记录错文档次数/有效切换测试次数 | D01；第一批 I01。单次通过只支持该版本该场景 |
| 是否保护读后发生的新修改 | 外部编辑确实完成后，旧范围请求按契约拒绝且新内容保留；增加无外部修改的合法请求对照，避免“全部拒绝”也被当作正确 | D03；第一批 I02。Document Lease 与在途异常/Quarantine 另测，不能由 I02 推出 |
| 执行反馈是否符合真实效果 | 将请求预期、Action Response、独立检查到的实际效果三者对照；分别记录错误报成功、效果符合预期却因验证问题报失败/unknown，以及证据不足 | D05，及相关 Action 的计数/读回契约；第一批 M01–M03。独立检查可用确切范围、DOCX 有效格式和可见版面，不能只信被测检查器 |
| 是否最终完成用户要求 | 每个端到端任务按事先列出的内容、格式、目标与交付要求验收，并单列多余文档数量；执行回执成功不能替代此验收 | WorkBuddy E 类。第一批冒烟只验证固定执行链路，不算真实 Agent 任务成功样本 |
| 是否减少完成任务的成本 | 记录完整任务和首次可见进展耗时，分开发现/准备、执行、验证交付阶段；分别计工具往返、Action 数和可取得的上下文用量 | D02/D06/D10/D12；真实 Agent 固定任务基线，证明改善另需可比对照。D09 的路线优劣不能仅凭当前路线跑通推断 |

D04、D08、D13、D14、D15 等仍按测试方案的 D01–D15 矩阵使用各自的针对性证据。第一批五个最小场景只覆盖优先缺口，不等于验收所有设计点。

### 8.3 计数规则与原五项指标的修正

- **任务完成率**：在固定任务组、固定版本和环境下，报告满足当前任务验收条件的端到端首次运行数/已发起的端到端首次运行数。待核验、失败和发起后的阻塞分别列出，不能删掉后只统计成功运行；启动前阻塞另计，修复复测另计。样本很少时直接写 n/N，不宣称生产可靠性。
- **任务完成时间**：按测试方案第 1.3 节采集完整时间线。失败或未完成任务记录截止观察时长及状态，不混入成功任务耗时；缺少可见时间戳就标缺失，不能用 Action 耗时替代。120 秒不触发自动取消，也不单独决定失败。
- **Action 效率**：保留 Action 数作为描述数据，同时记录模型工具往返、重复发现、纠错及无效操作。只有目标、结果质量和保护要求相同才比较成本；不能靠省掉必要读取/检查来制造“更高效率”。
- **非法调用比例**：Task 请求结构拒绝与 Action 参数校验拒绝分开记录，以各自同层级提交次数为分母，分别列拒绝原因；没有对应提交则记不适用。测试故意构造的非法请求不计入 Agent 自发错误。taskId 冲突等另外分类，不全部当作 schema 不合法。
- **执行验证质量**：原“COM 成功与 Action 成功的比例”只能反映两层返回差异，不能直接代表验证准确性。先逐例记录真实效果与反馈是否一致；扩大样本后分别统计“返回成功但独立验收未满足契约”的数量/已独立核验的成功返回数量，以及“实际满足契约却因验证误判未报成功”的数量/已独立确认满足契约的操作数量。未取得独立证据的数量必须同时报告；正常的谨慎 unknown 不自动算误判。

机制用例优先使用明确断言：应拒绝时拒绝且未覆盖，属于用例通过；执行报成功但实际不符合契约，属于用例失败。首次小样本的作用是找反例、核清语义和补证据，不是计算一个漂亮的总体成功率。

### 8.4 第一批结束应交付什么

1. **逐例事实与证据**：冒烟及 M01–M03、I01–I02 的版本、前置状态、预期、请求/返回、真实文档效果、判定和证据链接。每例标通过、失败、待核验或阻塞，未运行的明确保留。
2. **问题清单**：哪些是实现错误、契约表达或读回限制、测试夹具问题，哪些仍无法归因；附最小复现和影响范围。M03 的计数语义若未明确，先记录契约待决，不能事后按实现调整预期让它通过。
3. **设计结论**：例如“该场景支持绑定能抵抗焦点变化”“等价行距引起验证误判”“尚不能解释格式 null”。明确对应原问题和指标，只写证据支持的范围；没有反例不等于证明设计必要或优于替代方案。
4. **下一批调整建议**：确定需要修复并复测的项、可继续的 WorkBuddy 场景和仍缺的证据。错文档、覆盖新修改等问题阻断相关写入场景；局部格式问题按影响范围决定，不要求所有问题清零才做任何端到端测试。

因此，第一批主要回答“执行侧的几个关键设计能否给出正确、可信的行为与反馈”。第二批再回答“真实 Agent 能否使用这些设计完成用户任务，以及花了多少时间和调用成本”。两批都服务于原问题的评价，但承担不同证据责任；是否更快、更省仍需可比基线。
