## 1. 测试目的

当前优先回答：**设计是否解决了当初提出的问题，代价是否可接受，新增设计之间是否存在冲突？** 再扩大验证当前 Word Skill 在常见文档任务中能否正确、可重复地完成操作，并在失败时准确报告已发生的效果。

测试依据是 [设计梳理](../shared/WPS_SKILL_DESIGN_NOTES.md) 的原九个设计点与新增 D10–D15，现行机制边界仍以 CONTEXT 与 active ADR 为准。原设计笔记中尚未协调的需求与契约差异单独记录，不静默选一边作为最终验收标准。

### 1.1 两类设计问题

- **机制是否成立**：切换活动窗口是否仍写对文件？旧范围是否被拒绝？重复请求是否只返回回执？用最小针对性测试直接验证。
- **收益是否成立**：Session 是否降低初始化成本？Task 与发现方式是否减少 Agent 往返和上下文？首次可见进展和整体完成分别耗时多少？需要计时、成本分解和真实 Agent 的可比对照，不能用正常功能通过代替。

端到端是设计验证方法之一，不是只能最后做的阶段；但普通“写一篇文章并保存”无法验证全部设计点。先按假设选测试，暂不直接铺开 14 个 Action 和 30 次连续运行。

### 1.3 整体任务目标与计时（当前讨论口径）

用户认为 10 秒目前不现实，提出暂不设限或放宽至 120 秒。当前方案暂停 10 秒硬门槛，先验证完成用户预期、没有打开多余文档，并如实记录首次可见进展和整体耗时。旧 10 秒要求保留在历史讨论/证据中，不再用于当前用例判失败。

**建议采用的观察口径**：首批不设产品耗时通过线；固定短文、简单编辑这类同规模任务，以 **120 秒总耗时**作为关注标记，从用户提交任务到完成验证并交付最终回复。超过时记录阶段耗时及原因，不仅因超过 120 秒就判功能失败，也不自动中止或重新提交。120 秒不是首次可见进展时限，也不是已确认的长期 SLA；如后续选择硬门槛，按同类任务的基线另行确定。

保留 `t_user_submit`、`t_skill_load`、`t_window_visible`、`t_first_content_visible`、`t_saved`、`t_final_done`。会话日志可直接取得的时间先记录；窗口和内容可见时间用录像/定时截图补充，报告时间精度，没有证据就留空，不把日志完成时间当作肉眼可见时间。标题可算实际内容，空白窗口与口头进度不算。

冷启动、WPS 已运行、目标文档已打开分别标记，不混作同一性能样本。当前阶段无需为满足旧冷启动前提关闭用户工作的 WPS；有独立测试条件时再补冷启动样本。服务正常波动计入；明确故障单列且保留记录。

不设产品耗时门槛不等于取消程序的启动/单 Action/工具等待超时。本轮不修改任何运行时 timeout；发生超时仍按真实结果和不确定效果规则处理，禁止为凑 120 秒而放宽保护或重放写入。

完整 Task 预先生成与及时显示内容可能有取舍，先测量，再判断是否值得调整。当前不为追求原 10 秒要求拆成重复新建或跨请求恢复未保存文档。

## 3. 怎么测

### 3.1 两条测试路径

**A. 原生 Task 测试：测执行能力。**

由测试程序准备固定输入，按 schema 生成 version 2 Task Request，通过 UTF-8 标准输入调用打包后的 `scripts/word.py --app word --task-stdin`。使用真实 WPS，完整保存请求、回执和日志；执行后做独立文档验收。测试程序可以保存请求副本作为证据，无需让 Agent 临时编写请求文件来完成交互。

该路径验证当前交付包实际可执行的能力，不绕过 Runtime 直接修改文档。已有测试脚本可复用，但须检查其验证范围和调用入口；使用旧 Action Session 接口的脚本只提供辅助证据，不能冒充新版 Task 入口测试。现有 `word/live_acceptance.py` 也明确只验证 demo，不代表全部 Word Actions。

**B. WorkBuddy 端到端测试：测实际使用过程。**

提供固定自然语言指令与测试文件，由 WorkBuddy 加载 Skill 并自行编排。记录用户要求、会话、schema 获取、命令与回执读取、交付结果。预期结果固定，但不要求模型输出完全相同的 JSON。此路径同时判定用户目标、调用流程和交付说明。

两条路径分别计数。若原生通过而 WorkBuddy 失败，保留请求与工具证据，再定位到 Agent 编排、宿主工具或接口使用；不先假设是模型或执行器故障。

### 3.2 固定输入与环境

实施阶段先准备以下夹具，本轮仅定义，不创建 Windows 测试资产：

| 夹具 | 固定内容与用途 |
| --- | --- |
| 简短正文 | `测试标题` + `甲段：订单 A-001，数量 12。` + `乙段：测试🙂，金额 3.50 元。`；核对中文、英文、数字、标点与 UTF-16 范围 |
| 编辑文档 | 至少三个已知段落，目标标记出现两次，另有不应被修改的段落；核对匹配范围和旁侧内容 |
| 结构文档 | 两节、已知页眉页脚及布局；核对节范围与链接行为 |
| 表格和图片 | 固定 3×3 文字数据，固定 PNG/JPEG，各自记录哈希；核对位置、文字、尺寸和替代文本 |
| 输出冲突目录 | 预置原名及编号文件，记录字节与哈希；DOCX/PDF 占用编号可故意不同 |
| 长文 | 200 个带序号的固定段落，触发小读取限额下的截断与续读；不依赖模型生成 |

冻结 Skill 包与 schema 哈希、Windows/WPS/Python/PowerShell/WorkBuddy 版本、字体可用性、区域设置和测试时间。WorkBuddy 还记录模型标识（若可见）及影响执行的配置，不导出凭据。

每批一个独立输出目录，每次用例使用新的文档副本和输出位置。首次运行与后续运行分别标记；不为制造“冷启动”而关闭用户的 WPS。测试同一已打开文档时，以明确文件身份定位，禁止依赖当前活动窗口。

### 3.3 单个用例的执行与验收

1. 写明输入、前置状态、请求步骤、预期状态/错误码、允许产生的效果和禁止产生的效果。
2. 校验夹具与目标目录，记录基线；一个新请求使用唯一 taskId。用例 ID 固定，运行 ID 与 taskId 每次变化。
3. 提交一次请求；查询或重复提交同一请求保持原 ID。未知结果不能靠换 ID 重跑。
4. 读取 Task Outcome、每个 Action Response、checks、stop 与 Session Outcome，核对实际执行数量与顺序。
5. 根据场景核对正文、结构、格式、文件及可见版式，形成逐条断言结果。
6. 记录判定与问题，再执行测试夹具清理；失败与复测各保留一次记录，不能用复测成功覆盖首个失败。

验收分三层，按用例适用范围执行：

- **即时读回**：全文/目标范围、修改次数、结构、格式和 revision。逐字核对仅做明确的段落换行规范化，不随意 strip 掉有意义的空白。截断时续读同一 revision 的 remainingRange；动态续读由测试程序保留的独立只读 Action Session 完成，明确记为辅助验证，不能跨 Task 复用旧范围。
- **持久化结果**：保存后的 DOCX 包可读，正文、表格、图片关系及相关 XML 属性与预期一致。必要时重新打开已保存的明确文件做只读核验。原文件哈希只用于未授权修改的输入与占位文件，不能要求被授权修改的目标哈希不变。
- **可见结果**：在真实 WPS 或 WPS 导出的 PDF 中检查标题层次、字体、分页、表格与图片位置等。PDF 除文件签名外还须可解析、页数合理、文字/版面符合预期；签名正确不能单独判通过。

字体/加粗读回为 null 时，将对应断言记为“待核验”，用更窄范围、有效格式解析及视觉证据补充。DOCX 样式可能继承，不能只检查某个 run 是否直接写有属性。仅靠截图也不能证明字体名称。单位转换后的版式数值默认容差 0.1pt；契约有其他约定时使用契约标准并记录。

正常 Task 完成不会关闭用户文档。测试清理只能关闭本次测试明确创建或打开并拥有的测试文档，不关闭其他文档、不全局结束 WPS。若存在 unknown 或仍在执行的操作，停止有关用例，不抢先清理或绕过 Quarantine。

### 3.4 优先最小场景与操作分工（未执行）

“最小例”指只保留触发现象所需的一段文字和一个变化，减少全文、表格、检索、复杂样式等干扰，方便判断是写入、读回还是结果解释出问题。以下是五个场景，前三个核对格式，后两个核对真实文档干扰；它们不是只有五条 Action。

| 场景 | 固定步骤 | 要回答的问题 | 人工操作要求 |
| --- | --- | --- | --- |
| M01 等价行距 | 两份独立测试文档各写同一短段落，一份设 oneAndHalf，另一份设 multiple=1.5；读取实际行距、动作结果，核对保存后的布局 | 两种等价请求是否产生相同效果？是否仅因读回名称不同误报失败？ | 夹具、操作与读回可自动化；需要时人工只看两份版面 |
| M02 加粗/字体读回 | 写“测试标题 ABC”，明确字体和 bold=true；分别读纯文字范围、包含末尾段落标记的范围、单字符范围；对照 DOCX 有效格式 | null 是格式未生效，还是范围聚合导致无法用单值表达？ | 可自动化，不要求用户亲自选择文字或改格式 |
| M03 格式修改计数 | 已知未加粗的“测试文字”，只改为加粗，文字保持原样；记录前后实际格式、changedCount 与 revision | 格式实际变化时计数是否漏报？Revision 另按当前内容/结构语义判断，不预设必须改变 | 可自动化；先明确计数预期，不顺便修改 Revision 定义 |
| I01 切换活动窗口 | 创建测试 A/B；自动化绑定 A，测试控制程序把 B 激活，再要求对已绑定文档写入固定标记；检查 A/B | 活动窗口变化后仍修改 A，B 是否完全不变？ | 可由桌面自动化激活 B；用户不必手动切窗口 |
| I02 外部编辑 | 自动化读取 A 的目标段落与 revision；独立测试操作者把该段改成另一段已知文字；原 Session 提交旧范围替换；核对拒绝和外部文字保留 | 检测到内容已变时，是否阻止旧依据覆盖新内容？ | 可由独立测试程序直接编辑确切 WPS 测试文档，或桌面自动化输入；无需用户手打 |

I01/I02 操作的是真实 WPS 测试文档，不是仅修改 Mock 对象。I02 的独立编辑刻意发生在被测 Session 之外，模拟用户不受 Document Lease 约束的编辑；不能用第二个受 Lease 限制的 Skill Session 代替，否则测到的是 Lease 拒绝而非 Revision。测试程序要精确控制“已读完→外部编辑完成→提交旧范围”的时序，必要时用低层测试 Session，不能在生产 Task JSON 中新增暂停或回调能力。

优先全部由测试程序操作并采证。若交互桌面不可用，准确记录环境阻塞，再讨论人工协助；不提前把切换和输入操作分配给用户。实际人工键盘/鼠标操作可作为后续体验确认，不是以上机制首测的必要前置条件。

### 3.5 正式开始后的首批顺序与分工（计划，未启动）

**第一批：脚本驱动的机制验证。** 由 Codex 编写/复用 Python 用例程序和 Windows 启动/观察辅助脚本，经现有 SSH `win` 同步到独立测试目录，核对当前 Skill 包哈希，在真实 WPS 中执行。不会要求用户逐条粘贴命令。

1. 只读核对环境、版本、登录桌面和输出目录；准备固定夹具及逐条断言。
2. 跑一次最小新建→写入→读回→保存冒烟，确认执行和证据采集通道；它是通道检查，不重新展开整套功能验收。
3. 依次执行 M01 行距、M02 字体/加粗读回、M03 纯格式修改计数；每个先一次，保存请求、返回和独立观察，有异常先缩小/记录，不立即放大样本。
4. 执行 I01 切 B 后写 A、I02 外部改文后提交旧范围；由独立测试控制程序制造精确时序，检查原/外部内容和拒绝结果。
5. 自动收集日志、回执与产物，拉回本地，更新执行/问题台账；仅清理明确属于本次测试的文档和辅助资源。

普通功能路径优先使用打包后的 v2 Task stdin；需要控制读取与外部干扰之间时序的用例通过低层测试 Session 操作，注明它验证机制而非 Agent 入口。被测修改仍走正式 Action，实现层不因测试新增绕过校验的能力。

需要可见窗口、激活和输入的用例，在已登录的 Windows 交互桌面执行。已有旧 harness 使用 `LogonType Interactive / RunLevel Limited` 的临时计划任务作为启动方式，可在核查后复用其模式；不能只在 SSH 后台运行就宣称桌面干扰已发生。启动器须适配当前文件名、路径、超时和清理策略，不能直接无审查重跑旧脚本。

**第二批：WorkBuddy 真正的 Agent 端到端试验。** 初步选择 E01 固定短文、E02 已有文件修改/排版、E04 同名交付。由 WorkBuddy 根据自然语言自行选择 Skill、读取 schema、构造请求并解释结果；Codex 负责预置输入、发起/观察、取日志、验产物和记录。事先不向 WorkBuddy 提供替它编排好的 Task JSON，否则验证不了 Agent 的设计使用效果。

目前已验证可用的是 SSH 同步/执行/取日志，以及 WorkBuddy 独立沙箱 IPC 执行探针。该探针使用 RunExecutable 执行已有请求，没有驱动真实模型对话，不能当作真实 WorkBuddy 端到端入口。

## 5. 执行顺序、样本量与暂停条件

当前顺序调整为以下三阶段，等待用户明确开始后实施；原先的 30 次连续运行移到第三阶段：

1. **设计与证据盘点**：按 D01–D15 审计已有测试/日志，固定可证伪假设、缺口与方法。明确保存授权分歧；没有明确保存指令的争议场景暂不作产品验收，先使用显式授权场景。冻结版本，准备夹具、预期结果、可见进展采证与清理方法。
2. **针对性设计验证 + 少量端到端试验**：先补绑定、Revision、Lease、执行结果、Task 顺序/停止、回执及换名的关键缺口；隔离的故障模拟注明证据层级。选 E01 新建、E02 编辑、E04 同名交付作为固定任务，各跑 3 次，观察发现/编排收益、额外文档与首次可见进展；E01 标记冷/暖启动，当前不强求旧冷启动前置条件，其他条件分列。9 次仅作探索，不估计长期成功率。对照试验存在合适基线时再添加，固定模型、输入与工具条件，一次只改变所评估因素，并交替运行以减少顺序偏差。
3. **扩大功能与稳定性验证**：针对性验证没有未处置的严重风险后，再展开 F/P/N 全部用例以及 E03/E05。三个代表性成功链路各串行重复 10 次，共 30 次；每次独立夹具并检查内容、交付、资源，视觉检查各类首末次和异常产物。若第二阶段显示关键目标不满足，先决定调整设计还是继续验证独立部分，不盲目放大样本。

当前按第 1.3 节建立耗时基线，120 秒仅为简单固定任务的建议观察线；首次可见进展不设硬门槛。记录 Action、Task 命令、完整用户任务三个层级；重复场景分别报告最小/中位数/最大值。不同任务不混算有代表性的 p95；30 次整体数字只能作附录，不能外推吞吐或尾延迟。记录首末窗口资源与耗时趋势，不把少量波动直接称为泄漏或性能退化。

若没有可比旧版本或替代接口，D06/D10/D12 只报告当前表现与成本，不声称因果收益已证明；不为对照关闭保护机制，不要求先重做所有替代方案才能继续。

出现错文档、越权覆盖、内容丢失、结果不确定、操作仍在运行或清理无法证明完成，立即暂停该批相关写操作，保留现场并只读核验。普通确定失败先隔离用例；可继续不共享受影响状态的独立用例。仅缺失视觉或持久化证据时记待核验，不用重复写入来补证据。

## 6. 通过标准与问题处理

### 6.1 单例结果

- **未执行**：还没运行，或历史证据尚未在本轮复测。
- **通过**：该例全部必需断言与证据符合预期；预期拒绝用例也可以通过。
- **失败**：实际行为明确违反该例已确定的预期。
- **待核验**：执行发生，但现有证据不足以判定，例如格式 null 或缺少产物验收。
- **阻塞**：环境、夹具或工具阻止有效测试；不计作功能通过。

单独保留原始 Task Outcome 和 Session Outcome。用例“通过”不要求所有 Task 都 succeeded，例如 N03 的预期冲突是成功验证保护行为；反之 Task succeeded 也不保证用户目标或视觉验收通过。

### 6.2 分阶段结论门槛

设计阶段按 D01–D15 分项给出证据范围、机制/收益结论和待验证项。D01/D03/D04/D08 等关键保护边界存在反例或严重证据缺口时，不宣称可靠性已验证；收益缺少对照不等于功能失败，也不能写成收益成立。完成用户预期与是否有多余文档分别判定，首次可见进展和总耗时作为观察指标；不再因超过旧 10 秒门槛判失败。

以下为第三阶段功能批测的门槛，不用于增加整体用户任务的独立成功条件：

- F/P/N 展开后的必测用例及 E01–E05 全部有明确结果，不能遗漏或用历史记录补数。
- 要报告“首轮通过”，必测用例须全部通过；30 次重复全部符合预期，且没有未解释的资源清理失败。
- 存在失败或待核验时，只报告已通过的范围和未满足的条件，不以平均成功率掩盖错文档/覆盖/丢内容。
- 整体耗时和首次可见进展作为基线，简单任务超过建议的 120 秒观察线单独标记；明显递增或长尾须分析，不据此给出大批量无人值守承诺。

### 6.3 问题分类与跟踪

记录先区分事实、假设与确认原因。分类为：执行实现、契约/读回、Agent 编排、宿主工具、夹具/测试程序、环境、产品能力边界。错误码出现本身不是缺陷。

严重程度：S0 为错文档、未授权覆盖/内容损失或不确定写操作被重放；S1 为核心能力无法完成或错误报告成功；S2 为部分内容/格式/流程不符合要求；S3 为非阻断体验与效率问题。实际定级依影响范围判断，不能只根据错误码。

本文件保留测试观察和证据索引。按仓库约定，确认需修复的问题后续关联 GitHub Issue 作为正式跟踪源；本轮仅制定本地方案，不发布 Issue。不要把多个根因未知的现象合成一个缺陷，也不要因原有问题存在就重复建 Issue。

修复后，追加新运行记录、版本哈希和对应最小回归结果，再跑受影响的组合场景。原失败保留；不得在一个未标注版本变化的批次中混用修复前后结果。
