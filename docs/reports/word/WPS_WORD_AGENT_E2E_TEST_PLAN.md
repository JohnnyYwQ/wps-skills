# Word Agent 端到端测试方案：20 例

状态：方案与提示词已整理，尚未启动本轮测试。使用当前 14 Action 正式方案，不使用拆分实验包。

## 执行与统计口径

- 每例一个新的 WorkBuddy 会话，由自然语言提示词启动；不指定 Action、JSON 或内部实现。
- 使用同一构建产物、同一模型设置、同一 Windows 环境；记录 Skill/contract/代码版本或哈希。测试开始后不途中文档调优。
- 实际发送时仅替换下文 `{{ROOT}}` 为本轮独立 Windows 绝对目录，例如 `C:/wps-agent-e2e/run-日期编号`。提前创建 input/output 目录；所有已有文件都是测试副本。
- 主流程：提示词 → Skill → schema 查询 → 请求 → Task Response → Agent 最终汇报。允许为理解内容先读取、再提交修改 Task；不规定必须只有一个 Task。
- 不人工改 JSON 或帮助 Agent 修复。已失败/拒绝/unknown 后不自动重试；若 Agent 违反要求重试，保留首次失败，另记违规，不能用后续成功覆盖首次结果。
- 参数拒绝、未提交、无确定回执均计入用例总数。任务仍运行时标为 pending；观察上限 10 分钟，超出记超时/未确认，保留现场，先确认不再运行再开始下一例，不按“超时”推断回滚。
- 文件存在性、字体、权限、WPS 可用性在测试前统一准备，准备时间不计入用例。假定所要求字体已安装。
- schema 截断、查询次数、工具绕路、额外回读作为诊断，不直接代替 Task 成败判定。
- 图片尺寸与分页计数暂不纳入重点；E11 查看实际页面方向/分节效果，不使用分页计数作额外门槛。

## 成功判定

1. 自动执行通过：收到完成用户目标所需的全部 Task Response，均 `state: completed`、`outcome: succeeded`，无失败或 unknown。若 Agent 只做了读取就声称完成修改，则即使已有 Task 成功，也标记“目标完成存疑”，交人工检查，不能将它当成端到端通过。
2. 人工粗审通过：用户核对下面每例的内容和可见效果，确认基本符合需求。漏写内容、没有保存所需产物、改错位置等由人工审核判定。
3. 端到端通过：自动通过且人工通过。未人工审核时保持“待审”，不算已经通过。

Action Response 用来定位失败的具体步骤和错误。默认信任 Action 内部回读，不增加额外自动文档效果检查。长文是否基本达到要求也交人工粗审；不以独立自动字数检查取代约定的成功标准。

汇总：用例自动通过数/20、人工通过数/已审数（并列待审数）、端到端通过数/20；另报 Task 成功数/已提交 Task 数、Action 成功数/已执行 Action 数，单列 rejected、not_executed、unknown，不能混用分母。

## 时间与证据

以单调时钟或已校准的时间戳计算：

- T0：发送提示词；T1：首次 Task 请求开始提交。
- 每个 Task：JSON 进入执行入口至 Task Response 返回；读取现有 trace 的通信时间、逐 Action 时间、其他执行开销，避免把嵌套时间相加重复计算。
- T2：最后一个必要 Task Response 返回；T3：Agent 最终汇报完成。
- 输出 T1−T0、T2−T0、T3−T0、T3−T2；多 Task 另列各 Task 间 Agent 推理/编排耗时。
- 同步保存查询次数、schema 输出字节/截断、Task/Action 数量、每次请求和回执、失败步骤、产物路径。只采公开工具调用/响应和最终文本，不采模型内部推理。
- 人工审核时间不计入 Agent 时间。若出现澄清，分别报告总等待和扣除用户等待后的时间。
- 报告每例耗时、整体中位数、最大值；长文、已有内容理解等分类比较，不用平均数掩盖卡住案例。
