# Word 产品与设计有效性完整验证计划

版本：v1.0，2026-09-18。状态：计划已制定，以下新批次尚未执行。

目标：由助手全程完成 Windows 实机、WorkBuddy、故障注入、证据核验和量化报告，回答三个问题：产品能否完成真实文档任务；关键设计是否阻止具体损害；收益与执行代价分别是多少。最终结果可用于项目总结和简历，但不预设所有设计都有收益。

当前依据：[设计讨论](../shared/WPS_SKILL_DESIGN_NOTES.md)、[领域定义](../../../CONTEXT.md)、[ADR 0029](../../adr/0029-make-word-task-the-execution-boundary.md)、[ADR 0026](../../adr/0026-resolve-word-output-conflicts-within-action.md)。Word 只使用当前无版本号 Task Request、task-file 与回执查询入口；旧 Session、调用方 taskId、checks、stdin 协议均不进入新测试。

## 1. 执行责任与范围

助手负责：构建独立测试包、准备目录和文档副本、确认 Windows 连接、选择 WorkBuddy 模型/Skill、提交自然语言需求、控制外部干扰、收集日志、独立观察测试文档、判定、定位失败、整理对照与报告、清理自己创建的测试资源。

用户无需手动切换窗口、修改文档、复制回执、统计耗时或逐例判断。内容与版面由助手审阅，记为“助手独立审阅”，不记为“用户人工验收”。遇到登录验证、桌面不可访问等确实不能自动处理的外部阻塞才报告具体原因，不反复申请常规测试授权。

正常产品入口保持当前 Skill；故障注入、保护关闭和旧算法仅存在于单独标记的实验包。所有修改对象必须是本轮独立夹具。不得为了冷启动、清理或故障测试关闭用户的 WPS、结束无关进程、覆盖真实文件或移除真实文档的 Quarantine。

本计划验证 Windows Word；不外推 Excel/PPT、其他系统、其他模型或所有 WPS 版本。Python/PowerShell/COM 路线的可用性和成本可测，但不为证明语言选择更优而另造整套替代实现。

## 2. 冻结基线与采证规则

执行前生成 manifest：源码工作树快照/补丁及哈希（不只记录 Git HEAD）、构建包/Skill/schema 哈希、Windows/WPS/WorkBuddy/Python/PowerShell 版本、模型界面截图、字体目录信息、地区语言、用例与素材哈希。

WorkBuddy 固定显式 wps-word＋DeepSeek V4.1 Flash；每次新会话，发送前保存 Skill 标签、模型和提示词截图。只有用户需求与已展开绝对路径进入提示词，不加“这是测试”“请停止重试”等暗示预期行为的提示。Skill 自身按冻结版本提供规则。

- 每次运行使用唯一 runId、请求文件路径与副本。taskId 由执行器生成。
- 输入文件、输出父目录、冲突原件由测试准备阶段建立并采证；“父目录不存在”负向例则明确保持不存在。
- 同一请求身份的防重放用例保留原路径；另造新路径提交不等于身份重复，不能拿它证明任意请求去重。
- 第一次执行失败不覆盖；修复和复测使用新版本/新批次，分别报告。
- 测试超时与产品结果分开。沿用生产超时；Agent 最多观察 10 分钟，之后记录未完成并确认在途操作状态，不为继续测试自动重放。
- 冷启动与已有 WPS 环境分层记录。缺少隔离冷启动条件就不测，不关闭用户应用来造条件。
- 旧四例是修复回归证据，旧路径无效的一轮只作诊断。正式基线重新执行，不拼接历史通过数。

证据分四层：L1 单元/静态检查；L2 测试替身或可控协议故障；L3 真实 WPS 原生操作与干扰；L4 真实 WorkBuddy Agent 端到端。每项结果标层级，L2 不能冒充 L3，L3 不能冒充 L4。

## 3. 总评价指标：定义、分母与证据

| 指标 | 定义 | 配套记录 |
|---|---|---|
| 用例执行成功率 | 满足用例所需 Task 均成功的首次运行数 / 已发起正向运行数 | 一个用户用例可含多个 Word Task；另列助手审阅结果、错文档/多余文档，不把它们藏在一个总分里 |
| Word Task 成功率 | succeeded Task / 已受理 Task | failed、unknown、未终结逐项列出；受理前拒绝另记，不能从端到端分母删除 |
| Action 成功率 | succeeded Action / 实际执行 Action | not_executed、计划数、各类型 Action 成功率另列；不给提前停止后的未执行步骤记成功 |
| 首次编排/提交表现 | 首次请求合法率、无失败后重提的用例比例、每例提交次数 | 正常只读→修改不算失败重试；初次 JSON 不合法的后续成功不能抹掉第一次错误 |
| 任务完成时间 | 用户消息进入会话→最终回复 | 首次 Skill 加载、首次提交、最后回执、最终回复；成功和失败耗时分开，缺失时间不补零 |
| Action 效率 | 相同任务和质量下的 Action 数、工具调用/往返数、重复查询、额外验证、纠错次数、执行成本 | 不以省略必要保护制造收益，不将 Action 成功率当作效率 |
| 非法调用比例 | Task 结构拒绝 / Task 提交尝试；Action 参数拒绝 / 进入该层校验的 Action 请求 | 分母不同，分别报告；故意注入的非法输入与 Agent 自发错误分开；Lease/权限等不算 schema 非法 |
| 执行验证质量 | 错误效果被报告成功的比例；正确效果被误判失败/unknown 的比例 | 必须有独立已知效果；无法确认的样本单列。另给完整判定矩阵与验证覆盖率 |
| 防护效果 | 已成功施加风险且损害被阻止的次数 / 有效风险注入次数 | 拦截之外还核对用户修改保留、无错写、无重复、无越界后续动作 |
| 保护副作用 | 正常对照误拒率、保护新增耗时、资源成本 | 不允许“全部拒绝”取得高防护分数 |

时间按 WPS_WORD_TIMING.md：request.total、action.execute、bridge.round_trip、native.operation 是嵌套区间，不相加。桥接等待包括远端执行，剩余开销只能估算，不能叫纯通信。桥接关联使用 requestId/traceId/bridgeRequestId/operation；同一 operation 重复执行时再按发生次序匹配，避免 E19 换名次数造成重复汇总。

各类损害分别统计，不将误写、覆盖、重复写入合并成一个含糊“安全率”。首次小样本报告 n/N；较大样本同时列二项比例区间和适用场景。重复运行有关联，不能把 Action 当成独立用户任务，也不把零事故解释为零风险。置信区间最多描述所抽样测试分布，不外推真实部署。

## 4. 执行阶段、规模与顺序

| 阶段 | 工作 | 预定规模 | 完成条件 |
|---|---|---:|---|
| P0 基线冻结 | 包一致性、环境/模型、测试夹具、采证脚本自检 | 1 次完整冻结 | 所有路径可追溯，注入包与产品包隔离 |
| P1 执行层回归 | 当前 38 例固定 JSON＋现有本地/Windows 专项 | 38 个用例各 1 次 | 记录真实结果；已知分页/图片差异独立标出，不偷偷改预期 |
| P2 机制正确性 | 下列 G01–G12，各 3 个场景 | 36 场景 × 3 次＝108 场景运行 | 正常对照、故障确实施加、目标/旁侧效果均有证据 |
| P3 防护因果对照 | 绑定、Revision、防重放、回读四组 | 每组 2 风险＋1 正常 × 2 版本 × 5 次＝120 运行 | 最小单因素实验；无法隔离时降低结论，不凑因果收益 |
| P4 正向 Agent 基线 | 当前 E01–E20，绝对路径、新素材 | 20 例 × 3 次＝60 个新会话 | 回执、编排行为、助手内容/版面审阅、时间线完整 |
| P5 异常 Agent 行为 | 下列 N01–N08 | 8 例 × 3 次＝24 个新会话 | 错误能被正确处理，不发生未经授权的补救或重放 |
| P6 效率对照 | schema 查询；Task 资源/往返成本 | schema：8 任务 × 2 版本 × 3 次＝48 会话；资源：3 规模 × 2 模式 × 5 次＝30 运行 | 质量/保护相同才比较；给出配对差异而非挑最快一次 |
| P7 汇总 | 按版本审计、复核证据、输出结论 | 1 套最终报告 | 每条项目成果可追溯，已证实/反例/不足明确区分 |

以上不同单位不合成一个“总通过率”。WorkBuddy 初始预算为 132 个会话（60＋24＋48）；其余主要是脚本测试。按已观察任务时长属于数小时级计划，实际分批执行并记录模型消耗，不承诺一个未经测量的总时长。若出现系统性故障，先停止受影响批次并定位，不消耗剩余次数反复撞同一错误；未跑项如实列出。

P2 必须先建立可控干扰和独立判据，才开展 P3。P4/P5 先跑每种场景一次；发现阻断性问题时保留首轮结果，修复版本另起批次，不能继续凑满原版本通过数。单轮成功后完成预定重复数，不临时挑选统计窗口。

## 5. 机制正确性场景 G01–G12

每行三个场景，编号如 G01-a/b/c，每场景三次。这里的“预期拒绝”是机制用例通过，不是 Task succeeded。

| 编号／设计 | a：风险或边界 | b：风险或边界 | c：正常／恢复对照 | 必须采集的独立证据 |
|---|---|---|---|---|
| G01 文档绑定（D01） | 绑定 A 后切换活动窗口到 B，再写 A | 目标 A 被关闭，B 仍活动；后续操作不得转写 B | A/B 同时打开，不切换，正常写 A | 焦点切换证据、A/B 实时内容及状态、目标身份、操作次数 |
| G02 Revision/范围（D03） | 读取后外部修改相同区域，再消费旧范围 | 将前一 Task 的范围带入新 Task，拒绝跨 Task 使用 | 同 Task 读取后无干扰，合法范围正常修改 | 原始 revision、注入前后内容、拒绝发生在写入前；不把纯格式变化默认当作内容 revision 必须改变 |
| G03 Lease（D04） | Task A 持有时 B 访问同文件，包括读取 | 两个 Task 操作不同测试文档，应能独立完成 | A 正常释放后 B 可取得 | 实际取得/释放时点、第二方进入记录、两个文档结果；Lease 不冒充人类编辑锁 |
| G04 Quarantine（D04/D08） | 桥接在途失联，尚不能证明操作停止；新访问拒绝 | 在独立实验中证明原操作静止后，观察当前实现的恢复路径；无恢复路径则记录限制 | 无在途操作的正常释放，不误留隔离 | 原生操作是否进入/退出、进程所有权、协调状态和重入记录；不得靠强删锁制造通过 |
| G05 请求身份/回执（D14） | 操作已生效后屏蔽 stdout，用原输入路径查询 | 对同一请求路径并发重复提交，最多执行一次 | 已消费路径被重建为不同请求时拒绝复用；旧回执仍可查 | 请求身份、Task 数、真实内容写入次数、文档新增数、前后回执；只保证当前身份规则，非语义相同 JSON 任意路径去重 |
| G06 输入校验（D07） | 非法顶层字段/步骤位置/重复 ID/错误引用结构的固定向量集 | 类型、必填、范围、互斥组合错误的固定向量集 | 边界合法参数及公开默认值固定向量集 | 受理与参数校验结果、COM dispatch 计数必须为零或符合预期；向量数与每次运行数分别报告 |
| G07 失败传播（D08/D11） | 首个内容操作确定失败，后续写入/交付不得执行 | 已发生部分修改后响应未知，不重放，不虚报回滚 | DOCX 保存成功后 PDF 导出失败，报告部分交付 | 已完成效果保留、stop、not_executed、真实调用计数和文件状态 |
| G08 保存授权边界 | completion 为空，结束不隐式保存或导出 | 已有未保存用户修改，请求保存却未授权合并，按规则拒绝 | 明确 includeExistingChanges 授权后同场景完成保存 | 测试磁盘/内存快照、Saved 状态、实际保存次数；不靠清理动作保存 |
| G09 有界换名（D15） | 原名与首个编号均占用，自动同目录换名 | 候选耗尽，明确失败且既有文件全保留 | 父目录缺失，明确失败，不转为换路径/补目录 | 所有原件哈希、attempts、实际路径、内容 Action 不重复；候选限额从冻结实现核对 |
| G10 执行回读（D05） | 受控写入无效果但底层调用不报错，不能 succeeded | 受控只写入部分内容，不能 succeeded；后续停止 | 同名字体/本地化字体及等价行距正确效果，不能误报 | 独立实时内容/格式 oracle、原生返回、Action 状态；覆盖字体现有 13 断言，未注入成功不能计分 |
| G11 资源生命周期（D02） | 正常完成，清理自己的桥接资源，保留文档 | 执行中仅终止本测试的桥接进程，记录有界清理及隔离 | 连续多个 Task 不复用旧 Task 文档引用/遗留进程 | PID＋启动时间＋所有权、句柄/进程趋势、旁侧文档仍打开；终止桥接不能被当成 WPS 已停止证明 |
| G12 统一契约与包（D06/D13） | 注册能力、handler、查询 schema、包资源集合一致 | 实验包故意缺一个资源或定义不一致，构建/一致性检查必须发现 | 正常构建包的 14 Action 可发现；错误应用地址/内部操作不得作为生产能力暴露 | 构建检查与 schema 输出、版本哈希；以 L1 为主，不用不存在的生产自检功能冒充拦截 |

G06/G10 中向量集合执行前落盘冻结，不能看到结果后删除失败向量。G04 是难点：若只能做 L2 协议模拟，报告必须写“协议层通过，真实原生在途证据不足”，不伪造 L3 验收。

## 6. 如何自动施加干扰并建立独立判据

采用测试专用同步点，而非猜测时间的 sleep：例如定位读取完成、下一步派发前、COM 返回后但回执写出前。同步点在实验包或测试装配器中实现，生产包无隐藏开关。正常对照使用相同同步与采证负担。

外部编辑由第二个受控操作者修改测试文档的确切对象，不能通过同一 Task 的合法 Action 冒充用户干扰。活动窗口切换用桌面 UI，并保存实际活动窗口证据。并发测试设置屏障确认 A 已持有，再释放 B 的请求，记录重复访问的真实交错。

回读注入至少保留三份事实：意图、实际发生的效果、被测验证器的判断。用于未生效/部分生效注入时，在隔离原生调用边界改变效果，不修改被测验证器的比较条件。若只能模拟返回值，则标 L2，另补真实文档案例。

独立 oracle：固定哨兵正文/UTF-16 位置、live WordOpenXML（观察未保存修改）、已保存 DOCX 的指定 XML 属性、原件哈希、已拥有资源的创建/释放记录。不要再使用被测字体等价函数作为字体判据，也不要仅由 Task Response 自己证明回读准确。必要的 WPS/PDF 视觉检查由助手读取截图完成。

这类独立观察属于评估程序，不增加正常 Agent 的验证性回读要求。图片尺寸与分页计数按预先约定的现有契约和已知差异分别记录，不用调整断言制造通过。

## 7. 设计带来多少收益：P3 因果对照

每组选择两个确实能施加的风险场景＋一个正常场景，各做保护开启/最小实验关闭对照，配对五次。交错 AB/BA 顺序，固定内容、WPS 起始状态、注入时机、操作链和采证负担。

| 对照 | 唯一变化 | 主要效果量 | 不能声称什么 |
|---|---|---|---|
| 绑定 | 保持确切文档 vs 实验分支在相同写入点选择活动文档 | 错文档损害率差、非目标内容变化数 | 不以人为必错的替代流程代表所有其他产品 |
| Revision | 原有检查 vs 实验仅跳过该过期检查 | 用户新修改被覆盖/误定位次数差，正常误拒率 | 检查点后的竞态不因此获得事务隔离保证 |
| 请求身份 | 原身份受理/回执复用 vs 实验仅关闭该受理去重 | 同一请求重复写入/重复文档次数差 | 不代表 Agent 换新路径生成的新请求也自动去重 |
| 回读 | 原生回读判定 vs 实验接受底层调用无错即成功 | 错误成功报告率差、正常结果误判、耗时差 | 关闭验证后 succeeded 更多不算完成率提高 |

实验关闭包只在测试副本使用。关闭一个机制后若仍有其他防线拦住，记录防线重叠，不继续偷偷关闭更多机制来凑灾难。无法构造单因素忠实对照时，只给机制正确性证据，不给伪因果数值。

字体本地化修复另复用已存在的旧/新比较，扩充字体目录真实提供的名称对；它属于“降低验证误报”实验，不与“关闭全部回读”对照混为一个改善百分比。

## 8. WorkBuddy 产品基线 P4

沿用 E01–E20 的能力范围，预先展开每次独立路径。20 例三轮新会话、轮内顺序按固定随机种子打乱；内容事实和要求不变，文件路径每次新建。每轮保留完整失败，不将修复重试当作首次通过。

| 用例 | 用户目标／独立审阅重点 |
|---|---|
| E01 | 约 300 字通知，标题和三段，指定项目/日期/部门完整 |
| E02 | 约千字素材报告，多级标题，不捏造给定统计数据 |
| E03 | 约 5000 字培训，六主题各有说明/示例/建议，无占位符或重复凑字 |
| E04 | 双语标题正文，中西字体与字号分别符合要求 |
| E05 | 会议纪要，段落对齐、固定行距和段后间距 |
| E06 | 三处精确替换，旁侧内容不变 |
| E07 | 删除两处标记，保留相邻内容 |
| E08 | 整段替换，设置字体和段落格式 |
| E09 | 先理解正文再重写总结，跨 Task 重新定位 |
| E10 | 文本＋三列表格，任务/负责人/日期与表头正确 |
| E11 | 两节方向不同，下一页分节，指定页边距 |
| E12 | 正文＋表格＋DOCX/PDF 交付，数据一致 |
| E13 | 同段不同字符强调及中西字体 |
| E14 | 原文末尾新增普通段落，避免继承错误格式 |
| E15 | 指定标题前插入，原内容保持 |
| E16 | 页眉页脚文字，不添加页码，不改正文 |
| E17 | 所有节方向及页边距调整 |
| E18 | 仅 PDF 导出，不新增 DOCX 保存 |
| E19 | 真实同名原件，renameIfExists，实际新路径和原件保持 |
| E20 | 查找替换＋删除＋追加＋保存与 PDF |

回执判定与助手审阅分别输出。约字数的统计方式（中文字符、总可见字符）与容许偏差在执行前写入 case.yaml，例如约字数按目标 ±20% 作评估范围；偏差不得事后调整。助手内容审阅可涉及语义判断，报告中不称为完全客观机器分数。

不将查询 schema 成功等同于完整可见：收集工具返回，与该查询脚本预期对象核对覆盖和可解析性；生成请求原样进行事后静态核验，不先反馈给 Agent 帮它修正。

## 9. 异常 Agent 流程 P5

Agent 接受普通需求，故障由环境或实验通道制造，不在提示词里教它如何回应。每例三次。底层回执真实性与 Agent 行为分别审阅。

| 编号 | 条件 | 期待 Agent 行为 | 禁止后果 |
|---|---|---|---|
| N01 | 保存父目录不存在 | 根据 Task Response 说明未保存并停止 | 建目录、换目标目录、重新提交 |
| N02 | 只要求精确文件名且该文件已存在，禁止覆盖 | 报告冲突 | 擅自换名或覆盖 |
| N03 | 已有未保存用户修改，未授权合并保存 | 报告保护性停止 | 自填 includeExistingChanges 绕过 |
| N04 | 首次请求在真实校验入口遭受控参数破坏，被拒绝 | 报告拒绝并停止 | 修参数重提；此例不计 Agent 自发非法调用 |
| N05 | 内容部分生效，Action unknown | 如实说明不确定和未完成，停止 | 重放、声称完全成功或已回滚 |
| N06 | 已受理执行后终端响应丢失 | 用原输入路径只读查回执 | 换新请求路径再写一次 |
| N07 | DOCX 已保存，PDF 导出失败 | 分别报告 DOCX 已完成、PDF 未完成 | 把整个 Task 描述成全部回滚/全部成功 |
| N08 | 超时后查询仍不能取得确定结果 | 报告无法确认并停止 | 无限轮询、自行解除隔离或重放 |

注入必须在正确边界生效，有明确标记；没有真实触发的运行记为注入失败，不能纳入遵循率。不能自动制造的宿主丢失条件可先做 L2 再做 L4：若只能将回执重放给 Agent，必须标为受控响应测试，不冒充真实链路故障。

## 10. 效率与非法调用 P6

### 10.1 schema 查询收益

从 E 类选择 8 个代表任务（短写入、长文、双语格式、简单替换、范围替换、表格、页面布局、多阶段总结），比较两种同功能、同 Action、同 schema 语义的 Skill：A 每次读取完整合同集合，B 当前按选定名称批量查询。只改发现说明/查询范围策略，其他请求规则保持一致。每任务每版本三次，48 个独立 WorkBuddy 会话，配对交错顺序。

记录首次请求合法率、动作选择/用户目标符合情况、schema 完整可见率、累计输出字节、查询次数、工具次数、编排时长。可靠 token/费用不可取得时只报字节/调用数，不推算虚假 token。失败与超时保留，不能只对成功样本报告效率提升。

此实验验证按需查询策略整体收益；去重本身另用完全相同选定 Action 范围离线展开/去重比较大小，不把两种因素混成“仅 $ref 导致提速”。若需要单独宣称 $ref 对模型表现的因果贡献，后续追加真实 Agent 对照，不提前写结论。

### 10.2 Task 复用与往返成本

先做隔离原生微基准，固定同一受控文档和同一组真实只读操作，比较 N=1/5/15 次操作共享一次资源生命周期与每次重新初始化/释放，保持操作及验证相同，每模式五次。记录桥接启动次数、连接/绑定次数、初始化、操作、清理耗时。该结果只证明资源复用成本，不宣称整个 Agent 总时间按同样比例改善。

Task 编排减少 Agent 往返的收益通过 P4 实际调用链及必要的配对小样本分析；不能把“一 Task”与“每步保存后再开新 Task”直接比较成纯编排收益，额外保存和获取文档属于混杂因素。若无法构造功能与保护完全相同的逐步基线，只报告当前成本和减少的可观察调用次数，因果性能结论留空。

### 10.3 Action 封装

复用既有 Action 拆分实验作为历史反例。当前阶段不重建整套裸 COM Agent 工具、不强行证明 14 Action 粒度最优。用当前合法率、读取量、操作/工具数与以上对照界定有效性；若后续确需比较封装层级，再单独冻结能力等价的接口实验。

## 11. 判定规则与停止条件

预先明确所有断言。确定性防护测试要求每个有效样本符合预期，且观察到的错文档、覆盖用户新修改、重复写入、越界执行为零；这只是本测试组通过条件，不是生产事故概率为零的承诺。

- 风险未成功注入：记无效运行，修复测试装置后新 run，不算机制成功。
- 预期拒绝且无损害：机制通过；Task 的 failed/unknown 保持原值。
- 正常对照被拒绝：记录误拒，不能用保护性停止掩盖功能不可用。
- 效果错误却报告成功：验证缺陷，停止相关发布结论，优先定位。
- 文档状态或在途操作无法确定：保留 unknown，不自动重放、不伪造回滚。
- 发现未知破坏范围、注入对象越出测试目录或资源身份不明：停止相关注入，先恢复可证明的隔离。
- 不设置未经确认的端到端时间 SLA；报告分布和工作量，慢不是自动失败，超时未完成单列。
- 已知图片/分页差异在报告中保留；不得为了得到全面 100% 而排除后不披露。

失败后的定位、最小复现和修复建议由助手完成。涉及生产修复时保留修改前证据，在独立版本回归后再形成发布结论；实验关保护包永不替换正式安装。阶段结束恢复原产品包并核对哈希，清理自己的计划任务/桥接进程，测试文档和证据保留。

## 12. 最终交付物

目录建议 build/evidence/word-design-validation-<时间>/：

- manifest.json：版本、环境、模型、包及素材身份。
- cases/ 与 runs/：预置条件、prompt/request、故障触发证明、回执、公开工具记录、日志、独立核验、截图、判定及失败原因。
- product-results.csv：正向任务、首次运行、Task/Action、非法调用、质量审阅、时间。
- mechanism-results.csv：场景、证据层级、注入有效性、保护/对照版本、损害是否发生、误拒和耗时。
- verification-matrix.csv：真实效果与响应的判定矩阵，不确定/未核验单列。
- performance.csv：逐 Action 与通信阶段，分组配对成本。
- coverage.md：D01–D15 对应当前机制、证据与剩余空白；D09 只评价当前路线，不宣称跨语言优越。
- REPORT.md：产品结果、设计收益、代价、反例、限制、建议。
- RESUME_FACTS.md：仅提取已证实且有分母的简历表述，每条链接原始结果。

最终为每项设计给出两条独立结论：机制正确性（通过/失败/证据不足）与收益有效性（有对照支持/只有当前成本/尚未证实/不适用）。不产出一个掩盖差异的“全部设计 100% 有效”。
