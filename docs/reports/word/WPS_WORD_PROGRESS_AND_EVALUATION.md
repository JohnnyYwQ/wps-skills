## 除两项成功率还应记录什么

建议长期保留一个小而清楚的指标集，不追求指标数量。

1. 用户用例执行成功率：用户需求所需的所有 Task 成功；一个用例需要多个 Task 时仍只计一个用例。人工粗审另列，不与回执混成一个未经定义的分数。
2. Word Task / Action 成功率：分层定位。Action 分母用实际执行数，同时另列 not_executed 数量，避免靠提前停止缩小分母而隐藏问题。
3. 首次成功率和每例提交次数：避免最终成功掩盖 Agent 修改后重试；正常只读→修改的多 Task 编排不算重试。
4. 端到端时延：提示词进入会话→最终回复；另列首次提交前、Task 内部、逐 Action、最后回执后。多次样本再看中位数和高分位，四例无需包装为稳定 P95。
5. 异常流程遵循：发生失败或 unknown 后是否停止、是否如实报告已完成/未完成、回执丢失是否只查询不重复执行。无异常的成功用例不能证明此指标。
6. 覆盖与复现信息：模型、Skill/代码版本、环境、提示词、输入素材、文件路径、用例类型、运行次数；并保留任务请求、回执、日志。

本轮时延：E03 122.00 秒，E10 29.59 秒，E12 41.08 秒，E19 28.42 秒。Task 内部共 27.95 秒，Agent 会话共 221.08 秒，占约 12.6%；差值包含编排、工具和回复，不能全部叫模型思考时间。详细通信分析见最新报告。

## 是否需要验证机制有效性

需要，前提是希望说明“为什么成功、哪个设计带来什么收益”。目前整体结果证明系统在这些用例上可用，并未证明每个机制都有因果贡献。无需为所有机制逐一做消融，优先选择能解释正确率、误判率和时延的机制。

### 建议优先验证的三组机制

| 机制 | 要回答的问题 | 对照设计 | 核心指标 |
|---|---|---|---|
| 按名称查询 schema ＋公共定义去重 | 是否在保持编排正确的同时减少读取和时间？ | 同一版 Action/Skill/模型、相同任务，比较完整合并定义与所选 Action 查询。若单独评价去重，再比较同范围展开/去重版本；一次只改变一个变量 | 首次 JSON 静态正确率、schema 完整可见率、累计字节/有可靠记录时 token、查询次数、首次提交前耗时 |
| Task 内结果引用与统一执行 | 是否减少 Agent 工具往返，同时保持正确定位和改写？ | 在隔离测试中比较同任务单次计划＋结果引用与显式逐步调用同一组 Action；严格保持能力、回读和保存约束一致。无需拆掉生产运行时来测试 | 任务成功率、引用错误、Agent 提交/工具次数、总耗时。不同架构导致差异时明确混杂因素 |
| 回读验证及字体等价判断 | 是否能识别真正的未生效，同时避免把等价字体误报为错误？ | 固定请求，比较旧字符串判定与新字体身份判定；加入相同名称、本地化别名、真实不同字体、未知/歧义名称、字体目录不可用。读回失效的识别另以已知设置未生效的受控故障验证 | 正确成功、误报失败、错误放行、额外耗时；不能只用 succeeded 比例 |

字体机制已经有较强的局部对照证据：原始英文名在旧逻辑复现 unknown，修改别名判定后原请求通过；13 项 Windows 断言覆盖等价及拒绝分支。可以补充更多已安装字体及重复运行，不需要从零重做。

### 单独补一组异常流程验证

这组以协议/行为符合预期为成功，不应和正向文档完成率混为一个分母：

- 保存父目录不存在：Action/Task 报错；Agent 只报告，不创建目录、不换路径、不重新提交。
- 参数拒绝：如实报告，不自行改参数重提。
- 内容操作 unknown：保留不确定状态，不宣称回滚、不自动重放。
- 提交后 stdout/宿主响应丢失：只用原请求路径查询回执，不重复文档操作。
- 目标有未保存修改、过期范围/revision、保护性冲突：执行层按约定拒绝，Agent 不绕过。

成功标准是“受控错误被正确识别并正确停止”，不是把 Task 的 failed 改算 succeeded。用于验证回读可靠性的实验需要独立已知真值或定向观察；这属于评估方的实验判据，不是给正常 Agent 增加一轮文档回读。

## 推荐推进顺序

先完成本轮人工粗审；整理路径与素材后，在当前最终包上重跑完整 20 例，形成一份同版本正式端到端基线。随后针对上面优先机制做小范围、同模型同环境、独立新会话的配对对照，交错安排版本顺序并重复运行；记录每次结果，不只选最好一次。分别报告机制的收益、代价与未覆盖边界，再决定是否需要更多设计改动。

本文只整理现有证据和后续计划，没有启动新测试。
